Scope of this document

Architecture and modules

The design itself: how the system is decomposed, where each module physically runs, the eight decisions that shape it with the alternatives that were rejected, and the mechanisms a reviewer should test hardest. The case for building it at all — volumes, goals, risks and the decisions it needs from others — is in the companion Decision Brief.

1Context and current state

Today a Service Partner raising a query in the partner app reaches a human agent. There is no self-service layer, no automated resolution, and no structured capture of why the partner got in touch — the reason exists only as free text in a ticket and in the agent's head.

Three repositories are relevant, and the distinction matters because it constrains where anything can live:

RepositoryAudienceRelevance
empapiService PartnersWhere partner identity, wallet, leave and fines live. The only viable host if we do not build standalone, and the target of every Layer 6 call either way
adminInternal agentsRenders the agent screen. A UI concern — not a backend host candidate
app_serverCustomersNot a host, but a read source. Holds booking and order-side facts that some concerns need to evaluate. Layer 6 may call it for fact lookups only — never for actions, and never as a place any BOTIn module lives

2Solution overview

Every request follows the same seven-step chain, regardless of concern. What differs between concerns is configuration, not code path.

Tier is decided at step 5, at runtime, by the decision table — it is not a fixed property of a concern. The same concern can resolve at T1 for one partner and escalate to T3 for another, because the facts differ. This is a deliberate departure from the BRD's Table 9, which assigns a tier per concern; the two are reconcilable if Table 9 is read as the expected majority outcome rather than a constraint (open question O-4, §14).

Where the language model fits

The menu path needs no AI at all. Free text appears in exactly two places, and both are the same problem — turn unconstrained human language into one value from a fixed list:

  • Entry with no selection Add-on — not in the BRD
    The partner opens Help and types "mera aaj strike laga hai usko hatao" instead of tapping a menu. Nothing downstream can start, because a process is selected by name and we have no name yet. Handled by /classify-intent against the whole taxonomy. This path is not a stated requirement — see the callout below.
  • The reason step. Within a known concern, the partner explains why. Handled by /classify against that one concern's fixed category list.

These are different jobs at different scales, which is why they are separate endpoints rather than a mode flag. Consequently, Python is called based on input shape, not on tier. T0 and T1 never call it. A fully menu-driven T2 session calls it zero times. The classifier's confidence score is also the input to agent-connect trigger C — see §8.

Scope flag — free-text entry is an addition, not a requirement. The BRD specifies a menu-driven flow: the partner picks an L1 concern, then an L2 concern, and the system proceeds from there. Layer 5b and /classify-intent exist for a case the requirement does not describe — a partner who types their problem straight into the box before selecting anything.

It is included because the behaviour will happen whether or not it is specified, and because the alternative is a dead end for the partner. But it should be read as proposed additional scope: it carries its own endpoint, its own prompt, its own accuracy question, and an undecided low-confidence fallback policy (O-3, §14). Everything else in this design works without it. If it is cut, Layer 5b is removed and the menu remains the only entry path — no other module changes.

4Architecture decision records

Eight decisions that fix the shape of the system. Each states the decision, the mechanism it produces at runtime, and the constraint it imposes on everything built afterwards.

Three terms the records below assume. They are unfamiliar to anyone who has not used a workflow engine before, and nothing in §4 reads correctly without them.

A process definition is a file, not code. leave-fine.bpmn20.xml describes a conversation as a sequence of boxes and arrows — do this, then branch, then wait. Flowable reads the file and runs it. The application never contains a "which step am I on" variable, because the engine holds that.

A delegate is a Spring bean with one method. When the engine reaches a box that says "run some Java", it needs something to call. The file names a bean — flowable:delegateExpression="${fetchFactsDelegate}" — and the engine looks it up by that name. The string in the XML and the @Component name are the entire connection; there is no registration step and no interface to implement beyond JavaDelegate.

A User Task is a deliberate stop. Reaching one writes a row to ACT_RU_TASK and the engine returns. Nothing is held in memory and no thread is blocked. The instance stays stopped — through deploys, restarts and crashes — until something calls taskService.complete(...). That behaviour is the reason an engine is embedded at all, and it is why §13 tests it before anything is built on top.

ADR-001Orchestration runs on an embedded Flowable process engineDecided
Decision
Conversation flow for each concern is authored as a BPMN process and executed by Flowable, embedded as a Maven dependency in the host JVM. No separate workflow server is deployed.
Mechanism
On startup the engine creates approximately 25 ACT_* tables in the application database and scans src/main/resources/processes/*.bpmn20.xml. Each Service Task node names a Spring bean through flowable:delegateExpression="${beanName}" and calls it. A User Task node parks the instance in a queue and writes its state to ACT_RU_*; the instance survives JVM restarts and resumes when taskService.complete(...) is called, however much later that is.
Constraint
Process logic now lives in XML files rather than Java, so it is deployed, versioned and reviewed as a separate artifact. In-flight instances stay pinned to the process version they started on across a deploy. History level is fixed at AUDIT, not FULL, to bound write volume. Adding a concern means authoring a diagram, not writing a class.
ADR-002Business rules are DMN decision tablesDecided
Decision
The "is this a genuine case" logic for each automated concern is a DMN decision table with hit policy FIRST, not Java conditionals and not BPMN gateway expressions.
Mechanism
One Business Rule Task in the BPMN diagram binds a table by concern_catalogue.dmn_key. The engine passes the current process variables in as a fact map, evaluates rows top to bottom, stops at the first match and returns {tier, action} as new process variables. Cells are FEEL expressions — >= 0.7, <= 2, "TITANIUM","QUEEN", – for don't-care. The DMN engine ships in the same Flowable dependency as the process engine, so no additional library is introduced.
Constraint
Changing a threshold means editing one cell and redeploying the .dmn file — no recompile, no code review in the default path. These rows determine who gets paid. Under FIRST, row order is part of the logic: a catch-all placed above a specific rule silently swallows it. A review gate over rule edits is required before Wave 1 (Decision Brief, D-3).
ADR-003Language understanding runs in a separate Python serviceDecided
Decision
All natural-language classification happens in a FastAPI service that is deployed separately and holds no database credentials. Java never calls a language model directly.
Mechanism
The service exposes two endpoints and nothing else. Java calls them through ClassifierClient with a 3-second timeout wrapped in a Resilience4j circuit breaker. The response is validated against a Pydantic schema before it is returned, so Java receives either a well-formed result or an error — never a free-form string. On timeout, non-2xx or an open circuit, the calling delegate sets tier = T3 and the process continues to a human.
Constraint
The service can return a wrong category, but it cannot credit a wallet, write a ticket or read partner data, because it has no route to any of them. Misclassification is therefore bounded to a routing error, which the confidence threshold and the T3 fallback already handle. The cost is a second deployable in the pipeline. A well-isolated Java package would achieve much of the same containment; the physical boundary is chosen because it cannot be eroded by a later refactor.
ADR-004Partner-facing messages are templates, not generated textDecided
Decision
Every message a partner reads is a pre-written template. No language model writes partner-facing text at runtime, in any tier.
Mechanism
Each DMN action output maps to one template per supported language. /classify returns detectedLanguage (hi / en / hinglish) alongside the category, and Java selects the matching template and interpolates the variables — amount, date, fine reference — from values it already holds. Python identifies the language; Java produces the sentence. Translations are drafted with model assistance at design time and committed only after human review.
Constraint
Every sentence a partner can receive is reviewable before it is ever sent, and amounts and dates in financial messages come from the database rather than from a model. T0 and T1 make zero model calls as a result. The content set is finite and must be maintained: roughly 30 concerns × 3–4 outcomes ≈ 100 messages per language. Messages read as templated rather than conversational — accepted as the cost of determinism in messages about money.
ADR-005The action record commits in its own transactionDecided
Decision
TicketActionRecorder.recordAttempt() is annotated @Transactional(propagation = REQUIRES_NEW) and commits before any external call is made.
Mechanism
A Flowable Service Task executes inside the engine's own transaction. recordAttempt() suspends that transaction, opens its own, writes a ticket_action row with status ATTEMPTED and idempotencyKey = hash(ticketId, actionType), commits it, and returns. Only then does the delegate call the external system. If a later node in the process throws, the engine rolls back its own transaction — and the ATTEMPTED row remains, because it was never part of it.
Constraint
Without this, a rollback after a successful external call erases the only evidence that money moved, and reconciliation has nothing to detect. With it, the residue of a failure is an ATTEMPTED row with no completion — an actionable state rather than a silent one. This annotation is the single most load-bearing line in the design and is verified by a dedicated test rather than assumed (§13, U-3).
ADR-006concern_catalogue is the single source of the concern taxonomyDecided
Decision
The L1/L2 concern list exists once, as a database table whose columns point at every artifact a concern needs. No enum, no config file, no second copy.
Mechanism
One row per L2 concern carries l1_code, l2_code, labels, display_order, active, and four pointers: process_key selects the BPMN process, fact_provider resolves the ConcernFactProvider bean, dmn_key binds the decision table, togglz_flag names the kill switch. Plus default_tier and wave. Six consumers read this one row: the client menu, process selection, fact fetching, decision binding, the kill-switch check and wave planning. A single generic fetchFactsDelegate serves all concerns by resolving the provider bean named in the row.
Constraint
Adding an L2 concern is not a configuration change. The row is inert until the BPMN process, the fact provider bean, the DMN table and the response templates all exist. The catalogue removes duplication; it does not remove the build. §10 states this explicitly so the expectation is not set wrongly with ops.
ADR-007Automation is gated by a per-concern kill switch that fails to a humanDecided
Decision
Every automated concern sits behind a Togglz feature flag, checked after the decision table returns and before the action executor runs. Turning a flag off routes to T3 — it does not fail the request.
Mechanism
Togglz is a Spring-native library with no server component: a Feature enum, a JDBCStateRepository holding flag state in the application database, and an admin console at /togglz-console. The gateway after the Business Rule Task evaluates the flag named by concern_catalogue.togglz_flag, resolved at runtime with new NamedFeature(...). Flag state is read per request, so a change in the console takes effect on the next request with no restart. Togglz's percentage-rollout strategy provides the BRD's staged ramp directly.
Constraint
Flag off means "do not automate, send to a human" — never "error". The partner is still served; only the automation stops. Two consequences follow: resolving a flag by runtime string bypasses enum type safety, so startup validation must assert that every togglz_flag in the catalogue maps to a declared feature; and JDBCStateRepository persists current state only — not who changed it or when — so flip auditing is a required addition before Wave 1 (Decision Brief, D-7).
ADR-008Tier is computed per request, not assigned per concernDecided
Decision
tier is an output column of the DMN table, evaluated against the facts of the individual request. It is not a static property of a concern.
Mechanism
The decision table receives the classified category, the confidence score and every fact the provider fetched, and returns tier alongside action. An Exclusive Gateway on ${tier} then selects the branch. Two partners raising the same concern can take different branches in the same process: one with a clean claim history auto-resolves at T2, one with three similar claims this month routes to T3. concern_catalogue.default_tier is a fallback used only where no decision table is configured.
Constraint
Automation rate becomes a tunable rather than a fixed property, and medal-band differentiation is a table row rather than a code branch. It also means no static document can state the tier of a concern, including this one. Where BRD Table 9 assigns tiers per concern, that should be read as the expected majority outcome rather than a constraint on the system (O-4, §14).

5Data model

Six tables. Layer 2 is a package, not a service — zero HTTP endpoints and zero outbound calls, which makes it a leaf in the dependency graph and safe for everything else to depend on.

Two entities, not one, for a reason. A Help interaction exists before a ticket does. A T0 deflection creates a help_session and never creates a ticket — which is the BRD's Gate 1 made literal, and the reason T0 volume does not appear in ticket counts at all.

Write criticality is tiered deliberately. Four of the six are on the request path and must be synchronous. conversation_message is the highest-volume write and the least critical — it is the raw transcript, deliberately not what an agent sees first — so it is published as an event after commit and written on a separate thread. That keeps transcript volume off the partner's response latency without risking the records that matter.

Index required before Wave 1: ticket(sp_id, created_at). The claim-frequency read sits on the critical path of every T2 decision.

The client contract

Every response carries a nextStep descriptor — menu, dropdown, text, message or csat — plus its options or content. The backend owns 100% of the flow logic; the client is a thin renderer. The alternative puts flow logic in two places, where it drifts.

One mechanism worth stating because it is a real trap: after startProcessInstanceByKey(...) returns, Layer 1 must not read process variables. A completed process instance has its runtime row deleted, so those variables are gone. The process's final Service Task writes nextStep onto the help_session row, and Layer 1 re-reads it from there.

The agent handoff — chat, and two calls of unequal weight

T3 hands the partner to an agent in a chat system, not on a phone call. When the process reaches its User Task, the ticket is placed in an agent queue and the conversation continues in the same thread the partner is already in. The partner is not called back; they stay where they are and a human takes over the reply. The chat platform itself is not chosen yet, which is why Layer 8's deployable is marked TBD.

GET /tickets/{id}/escalation-context is called first, as the agent opens the conversation, and returns computed facts: category, confidence, the already-extracted reason, medal band, a recent-history rollup, prior actions, and which trigger fired. GET /tickets/{id}/conversation is secondary and lazy — behind a "view full conversation" control, not auto-loaded.

Deliberately not built: a model call to write a prose summary for the agent. extractedReason already is the summary, structured rather than prose, reused from the classification that already ran. A third model touchpoint to re-summarise what has already been extracted is scope creep, not a missing piece.

8Agent-connect triggers

The default is no agent. T0, T1 and T2 close without one. A human is offered only when one of five defined triggers fires — and holding those five to their stated conditions is what keeps the human-handled share inside the 10–20% target.

Triggers are cross-cutting: they belong to the session, not to the concern. That is a different shape from ADR-008, where tier comes out of the concern's own decision table. Reconciling the two is what this section specifies.

Why one decision point is not enough

The process today evaluates tier once, at the Business Rule Task, from the concern's own DMN table. That covers exactly one trigger — C's confidence threshold, which happens to be an input the concern table already reads. The other four need evaluation points the process does not have, and one of them fires after the instance is gone.

The two-stage decision

The resolution is to split what is currently one evaluation into two, and to add a gate on each end. Stage 1 asks "should a human take this regardless of the concern?"; stage 2 asks "what does this concern's rulebook say?" Stage 2 is the table we already have; nothing about it changes.

Stage 2 is a second decision table, not a column on the first. Injecting a repeatContact7d input into all 36 concern tables would work and is the wrong shape: one table missed is a silent hole, and every future concern inherits the obligation. A shared table evaluated first is one artifact to review and one place to change.

This is DMN's decision-requirements pattern — one decision feeding another — which Layer 4 previously recorded as unused. That call is reversed here: two decisions is the correct model once triggers exist.

Trigger A — dissatisfaction, and why it is the hardest

The other four fire while the process is running. A fires after it has finished. finalizeDelegate writes nextStep onto the help_session and the instance completes; its runtime row is deleted. The client then renders the CSAT prompt. When the partner taps No, there is no live instance to resume and no gateway waiting to branch.

Two mechanisms, materially different:

OptionHowCost
Keep the instance aliveReplace the final Service Task with a Receive Task waiting on a CSAT message event, then an Exclusive Gateway on the answerEvery ticket holds an open Flowable instance until CSAT arrives or a boundary timer expires. Most partners never answer, so most instances expire on the timer. At 50,000 tickets a month that is a large population of parked instances
Start a second processCSAT = No starts a short escalation process against the same ticketIdNothing parked at rest. The ticket now has two process instances in its history, and the audit trail has to be read across both

Neither is obviously right. The choice should be made deliberately rather than discovered during build — it is tracked as O-15 in §14.

The bounding rule

The bounding rule is not trigger A — it is the inverse, and it is what protects the target. On any T0–T2 case the partner confirms as resolved (CSAT = Yes), the "Talk to an Agent" option must be suppressed. Without it, every satisfied partner still sees a route to a human and the 10–20% ceiling stops meaning anything.

It must be enforced in ticket-closure logic, not left to agent or partner discretion, and not implemented in the client — a suppression rule that lives in the UI is a suppression rule that can be bypassed. Trigger B is the stated exception: a mandatory-human category routes to an agent regardless of CSAT.

Nothing in the current design implements this. ticket.csatResult is a recorded field with no logic attached to it.

What this requires elsewhere

The Python change is deliberately the cheapest available: sentiment and risk ride along as extra fields on a call that already happens, so T0 and T1 still make zero model calls and no new latency is introduced on any path. The limit is coverage, not cost — the classifier is invoked at the reason step, so a partner who becomes abusive at turn five passes through nothing that would notice. Evaluating E on every free-text turn is a larger change and is not proposed here.

Effect on the target

The 14% agent-connect figure in the volume data is described as a structural baseline — the floor, not the target. Triggers C, D and E all add to it. The clarification loop is the only mechanism in this section that pushes the other way: every low-confidence session recovered by a re-prompt is a ticket that does not reach a human. That makes the loop a rate control, not just a courtesy, and it is the reason C should not be built as a bare threshold.

9Money safety

T2 moves money with no human in the loop. Four independent controls, each covering a failure the others do not.

The hazard, stated plainly. A Flowable Service Task runs inside the engine's transaction. If a step after the external call throws, the engine rolls back — and the rollback erases our record that we called the external system. The external system does not roll back. The result is money moved and no evidence in our database that we moved it. Not a lost record: a financial reconciliation failure with no audit trail.

Idempotency keyUnique constraint on ticket_action.idempotency_key, generated as hash(ticketId, actionType)Retries and duplicate submissions. A repeat is a no-op, not a second credit

Kill switchTogglz flag per concern, checked after the decision and before the actionSystematic error discovered in production. Seconds to stop, and partners still get served — by a human
ReconciliationA Spring @Scheduled job summing ticket_action credits per partner against the actual ledgerEverything the first three miss. Alerts on any mismatch — target is zero, so any non-zero is actionable

Retry and idempotency are a designed pair, not two features. Flowable will retry a failed job; the idempotency key is what makes that retry safe. Neither is sound without the other, and reviewing one without the other misses the point.

POC Phase 8 tests the second control by deliberately constructing the failure: record the attempt, simulate a successful external call, throw from a later delegate, then assert that the Flowable transaction rolled back and the ticket_action row survived. If that test fails, the money-safety model needs redesign and the project stops there rather than continuing.

11What is code and what is configuration

The split is deliberate and worth stating precisely, because it sets expectations about who can change what without engineering.

What data to fetch is code. What to conclude from it is configuration. A fact provider is a Java bean because fetching correctly is an engineering concern. A decision table is a grid because concluding correctly is a business concern that will be tuned.

12Non-functional concerns

Observability Designed

Micrometer instrumented at each layer, exported via the OpenTelemetry Java agent into Prometheus and Grafana — or whatever the EKS cluster already runs, which is worth confirming before standing anything up (O-9, §14). Dashboards carry the success measures from the Decision Brief, with their alert thresholds attached.

Access control Not designed — D-7

Deliberately marked as a gap rather than hand-waved. The unresolved questions are concrete: who may flip a kill switch; who may edit a decision table that moves money; who may read a partner's transcript, which contains whatever they typed; and how the agent-facing surface authenticates to the context endpoints. This must land before Wave 1 go-live, not after — tracked as D-7 in the Decision Brief. Shipping a money-moving system with an unauthenticated /togglz-console is not acceptable, and the current design has no answer for it.

LLM guardrails Not designed

The classifier returns a category string that selects a code path. Nothing today validates that the returned category is a member of the expected enum, and nothing constrains what a prompt-injected free-text field could elicit. The mitigation is structural rather than clever — Python holds no credentials and can take no action (ADR-003) — so the blast radius is a misclassification, which routes to a human. Explicit validation still needs designing.

Data retention

conversation_message is the highest-volume table and holds whatever partners type, which may include personal information. Retention, archival and a PII policy are open (O-10, §14). Flowable history is capped at AUDIT level rather than FULL to bound its own growth.

13Delivery plan

Phase 1 — the proof of concept

One concern, carried end to end through every module the design needs. It exists to answer five questions that would be expensive to get wrong later. It is not a small version of the product — it is the shortest path that exercises Flowable, the DMN engine, the classifier, the action executor and the transaction boundary at once.

#QuestionAnswered byIf the answer is bad

Exit criteria are agreed before the numbers are known, which is the only way a threshold means anything: ≥ 90% classifier accuracy means the design holds; 75–90% means proceed with a raised threshold and a higher expected agent-connect rate; below 75% means rethink the approach. Either safety test failing means stop.

How the two blocking unknowns are answered

U-1 and U-3 are the only two whose failure stops the project, so each is settled by a spike before any product code depends on it — a throwaway program that answers one question and is then deleted. The deliverable of a spike is the answer and a written page, not the code.

U-1 — does a paused conversation survive the server dying?

When a partner's concern reaches T3 the conversation has to wait for a human, and that wait can run for hours. Across a wait that long the service will restart — a deploy, a crash, a pod recycling. The question is whether the half-finished conversation still exists afterwards and can carry on from where it stopped.

Written by hand, that means persisting the state, reloading it, and working out which step was reached. ADR-001 chooses Flowable precisely so none of that is written — which makes the choice worth nothing if the engine does not actually behave that way.

The test: start a process, let it park on a User Task, destroy the JVM without a graceful shutdown, start a new one, and complete the task. The same task must still be waiting, and the process must run to completion in an engine that never saw it start.

U-3 — is the payment record safe when a later step fails?

A refund is two writes and one external call. The service records "about to credit ₹X", calls the payment system, and the money moves. If any step after that throws, Spring rolls the transaction back and the record disappears — but the payment system does not roll back with it. Money has left and the database says nothing happened. Reconciliation finds a discrepancy with nothing to explain it.

The fix is one annotation: REQUIRES_NEW tells Spring not to join the engine's transaction but to open its own and commit immediately, so the record is permanently saved before the payment is attempted and no later rollback can reach it.

The test: record the attempt, simulate a successful external call, throw from a later node, then assert the engine's transaction rolled back and the record survived.

Both spikes must also contain a test that fails on purpose. Remove the annotation and assert the record is lost. Without that, the passing test may be passing for an unrelated reason, and nothing will notice when someone deletes the annotation months later. A test that only demonstrates the good case cannot protect the bad one.

One dependency worth naming: POC Phases 1–8 depend on nothing from Phase 0 except the test environment, so the data-labelling work is independent of the build. That labelling is also the step most likely to be dropped — and without it, Phase 10 produces an impression rather than a number, which forfeits the whole reason for running U-2.

Phases 2 onward

The shape of Phase 2 depends on U-4. An integration and a build are materially different pieces of work in Layer 6, and the rest of the phase cannot be scoped meaningfully until that audit returns.

If the business wants agents to reach partners by phone, this design needs revisiting. Layer 8 is currently specified as a chat handoff: the ticket enters an agent queue and the conversation continues in the thread the partner is already in. Nothing in the design places an outbound call.

Moving to voice is not a swap of one adapter for another. It adds a telephony vendor and its contract, DLT registration for outbound calling, a screen-pop mechanism so the agent sees the context at the moment the call connects, a call-outcome path back into the ticket, and a retry policy for calls that do not connect — none of which the current failure-mode table (§10) covers. It also changes what "resolved" means for a ticket, because a partner who does not answer is a state the chat model does not have.

The two context endpoints in §6 survive that change unaltered — they serve an agent view regardless of channel. Everything else in Layer 8 would be re-specified.

One input is still outstanding and worth naming: SP_Help_Flows.drawio — 51 flowcharts referenced by the BRD, not yet in hand. It is the most likely source of detail that would change O-1 and O-12.

The distinction reviewers most often collapse: the process engine remembers, the decision engine does not. The process engine is stateful — it writes ACT_RU_* rows, waits indefinitely, and survives restarts. The DMN engine is a stateless pure function: facts in, {tier, action} out. They ship in the same dependency and meet at exactly one place, the Business Rule Task.
