The decision this asks for

This brief is written to stand alone. A reader who finishes it should be able to approve, reject, or send back the proposal without opening the Engineering Design — which carries the architecture, the decision records and the module detail behind every claim made here.

A.1The problem

Every Partner Support query today is answered by a human agent. Most of them do not need a human.

In the May sample, 6,245 tickets — 12.46% of all volume — were one question: why was I fined for taking leave? The three largest concerns together account for 54.4% of volume. These are not conversations requiring judgement. Each is a lookup against data we already hold, followed by a decision that follows a written SOP, followed by a credit to a wallet.

Agent time spent on the first three rows is the cost this project removes. Strike appeals — deliberately placed in Wave 4 — stay with humans, because they are genuine judgement calls and automating them would be the wrong kind of efficiency.

A.2What we propose

BOTIn Mod puts a bot in front of every Partner Support query and hands to a human only when a defined trigger fires. Four tiers, decided per request at runtime:

TierBehaviourTicket createdExample
T0 DeflectAnswer from static content; conversation endsNo"Where do I see my payout date?"
T1 Auto-resolveRead our own data, state the answerYes"There is no fine on that date."
T2 Auto-actionRead data, apply a rule, move moneyYesRefund a leave fine
T3 Agent connectAssemble context, call the partner, hand to an agentYesLow confidence, or a judgement concern

The bot is not a chatbot in the conversational sense. It is a server-driven flow in which every step is a menu, a database read, a rule evaluation, or an action. A language model is used in exactly one place — turning free-typed Hinglish into one value from a fixed list. It never decides anything, never writes a message the partner reads, and structurally cannot move money (Engineering Design, ADR-003 and ADR-004).

A.3Goals and non-goals

Goals

  • Resolve the Wave 1 concerns without an agent, at the BRD's target of 86% bot-handled / 10–20% agent-connect.
  • Make every automated money movement auditable, idempotent, and individually reversible by a switch an ops user can flip in seconds.
  • Keep the business rules editable by the people who own them, without a code deploy.
  • Hand escalated partners to an agent who already has the context, rather than one who starts by asking what happened.

Non-goals

  • A general-purpose assistant. The taxonomy is closed: ~30 L2 concerns from the SOP. Anything outside it goes to a human.
  • LLM-authored partner-facing text. Responses are reviewed templates. See ADR-004 for why, and what that costs us.
  • Replacing agents on judgement concerns. Strike appeals stay human by design, not by omission.
  • New paid infrastructure. The workflow engine is a library inside our own service, not a platform to operate.
  • Changing fine or leave policy. This system automates the SOP as written. If the SOP is wrong, that is a separate conversation.

Phase 1 is deliberately shaped to fail fast. Two of its tests (Engineering Design §13) are designed so that if either fails, the correct response is to stop and redesign rather than continue building on a foundation that does not hold.

A.6Principal risks

RiskAssessmentMitigation
The classifier is not accurate enough on real HinglishGenuine unknown. Partners mix Hindi, English and transliteration in one sentence. Everything else in this design is conventional Spring Boot work; this is the part that could fail.Measured in POC Phase 10 against 150–200 hand-labelled real tickets, with exit thresholds agreed before the number is known (§12)
The fine-refund capability may not exist as an APIThe SOP documents the refund as an admin UI click path — Admin → Escalation → View SP Escalation → select date range → refund fine — not a service call. That is evidence, not proof, that Layer 6 is a build rather than an integration.An audit of empapi in POC Phase 0 settles it by inspection. Layer 6's interface boundary means the answer changes only that module's implementation, and it does not block POC Phases 1–8
Automated money movementT2 credits partner wallets with no human in the loop. A bug here is a financial incident, not a bad user experience.Four independent controls, described in the Engineering Design (§9): idempotency key, REQUIRES_NEW transaction boundary, per-concern kill switch, daily reconciliation. The POC tests the second one deliberately
Rules that move money are editable without a deployADR-002 makes this possible on purpose. It is also the sharpest governance hazard in the design: a one-cell edit to a DMN table changes who gets paid, with no code review.Unmitigated today. This is decision D-3. It needs a review gate and an audit trail before Wave 1, not before the POC
Two unfamiliar notations enter the codebaseBPMN and DMN are new to this stack. Process and decision logic move out of Java and into files that a Java reviewer cannot fully check by reading the code.Partially structural: BPMN and DMN are readable artifacts, so the logic is inspectable by anyone rather than locked inside Java. It still means the review skill has to exist somewhere, and today it does not
Layer 11 and Layer 12 are placeholdersAccess control and LLM guardrails are named in the architecture but not designed. A money-moving system with an unauthenticated kill-switch console is not shippable.Both are scoped out of the POC deliberately and in scope for Wave 1 — see the Engineering Design (§12). Tracked as decision D-7
Four of the five agent-connect triggers are not builtOnly the low-confidence threshold exists, and only in part. The rule that suppresses the agent option on satisfied cases — the single strongest control on the agent-connect rate — has no implementation at all.Specified in the Engineering Design (§8) as a two-stage decision with a pre-flight gate and a post-resolution gate. Until it is built, the 10–20% target is an aspiration rather than an enforced ceiling
