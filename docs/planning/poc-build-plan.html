BOTIn POC Build Plan

Eight concerns, twenty-six rules, every tier and every outcome type — API-driven, backend only. Built as the seed of the production service, not a spike.

0 of 0 done

Three decisions this plan is built on. Fact providers read a real read-only replica wherever the signal exists and a mock where it doesn't, with every gap recorded — so the signal audit is a build output, not a separate exercise. All writes go to mocks. No LLM key exists, so the classifier ships behind a stub and vendor selection runs as its own track (§3). And the codebase is the production seed: migrations, transaction boundaries, package structure and tests are built to keep.

Three inputs are not available, and the POC proceeds without them. Each has a workaround that keeps the work honest. What matters is that every substitution is named, isolated to one place, and recorded as an assumption — a guess written into a fact provider and forgotten is how a POC quietly stops meaning anything.

1 · The Transport path selector is unknown → derive it, in one named place. The likely reading of the mapping is that the three paths are three entitlement types: Path 1 a customer transport charge that never reached the partner, Path 2 a cancellation, Path 3 travel beyond the hub radius. So the selector becomes a computed fact — transportPath — written by TransportFactProvider and fed into the decision table as an ordinary input column.
Cost: the POC proves the three paths work; it does not prove a claim lands on the right one. The rule stays one method and one column, so the real answer is a small edit rather than a redesign.

2 · No read replica → build against a seeded local database with the real schema shape. Ask for a schema-only dump rather than access: it is DDL with no rows, carries no data risk, and is a far smaller favour to ask. Seed it with synthetic partners, bookings, violations and wallet states. Fact providers then write real SQL against real column names, and switching to the replica later is a datasource change.
Cost: the signal-availability register records signals as assumed rather than verified. It still produces the exact list of questions for whoever owns the data — which is most of its value.

3 · No historical ticket text → hand-write Hinglish fixtures, and accept that U-2 stays unanswered. The classifier sits behind a stub anyway because there is no LLM key, so this blocks measurement, not building. Twenty to thirty fixture strings exercise routing, the confidence threshold, the clarification loop and the degradation path. Base their phrasing on the concern names themselves — "Transport amount nahi mila", "Recharge kiya, pese cut gaye", "Job pe nahi jana" — which are real partner language.
Cost, and it is the real one: no accuracy number. Fixtures written by the person building the classifier will always classify well. That is not evidence. U-2 must be reported as not assessed, never as passed.

What this does not change: every architectural question the POC exists to answer — the transaction boundary, idempotency, the cap escalating rather than clamping, shared-service reuse, durable counters, the kill switch, degradation, pause-and-resume — is unaffected. Those were never waiting on these three inputs.

Deliberately excluded. No SP app, no agent UI, no telephony, no medal bands, no observability stack, no access control, and none of the other 30 concerns. Two exclusions are worth stating because they are easy to assume present: agent-connect triggers D and E are not built, and B only in its CSAT-exception form — A, the bounding rule and C's confidence threshold are in scope, and no production system is written to — every wallet credit, violation removal and strike recalculation goes to a mock.

One thing to confirm before step 1. Transport rules 2–8 are labelled Path 1, Path 2 and Path 3, but the mapping never says what assigns a case to a path. That selector is the first branch in the concern's decision table, so it has to come from whoever owns the mapping before the table can be authored.

3LLM selection and procurement

This track starts immediately and runs alongside everything else, because the decision has a lead time nothing else in the plan can absorb. The build does not wait for it — the classifier ships behind a stub from step one and the vendor becomes a configuration change.

Build the evaluation harness before shortlisting anything. A vendor-agnostic test set and scorer turns the choice into a measurement instead of a preference. Without it, selection collapses into whoever demos best.

3aDefine what the model has to do

3bBuild the harness

3cShortlist and decide

3dProcure and secure the key

Until a key exists, ClassifierClient talks to a stub that returns a deterministic category for known fixture strings and a low confidence for anything else. Every free-text path, every confidence threshold and every degradation route is fully exercised. The only thing that stays unmeasured is accuracy — and that is a number, not a design risk.

5The API surface

Backend only. Every case in the coverage matrix is reachable through these.

# Partner-facing
GET  /help/concerns                      → five L1 paths, from the catalogue
GET  /help/concerns/{l1}                 → active L2s under that path
POST /help/sessions                      → {spId, l1?, l2?, freeText?}
POST /help/sessions/{id}/input           → {value} for the current nextStep
GET  /help/sessions/{id}                 → current state + nextStep (reconnect)

# Agent-facing — chat handoff, no telephony
GET  /agent/tasks?queue=                 → waiting User Tasks
POST /agent/tasks/{id}/claim
GET  /tickets/{id}/escalation-context    → computed facts, loaded first
GET  /tickets/{id}/conversation          → raw transcript, loaded lazily
POST /agent/tasks/{id}/complete          → resolution + resume the process

# Operations
GET  /togglz-console                      → authenticated, even in the POC
GET  /actuator/health
GET  /internal/signals/register          → live signal-availability register

/internal/signals/register is not decoration. It reports, per signal, whether the fact providers are reading real data or a mock and why — which makes the most valuable POC output queryable instead of buried in a document that goes stale.

—Added: agent-connect triggers B (pre-flight), D and E, access control (Layer 11), guardrails (Layer 12), observability (Layer 9), the remaining 30 concerns

The remaining gap is the rest of the trigger model. With CSAT, trigger A and the bounding rule built here, what is still missing is trigger B’s pre-flight gate, trigger D’s cross-concern repeat-contact check, and trigger E’s sentiment and risk detection. D in particular needs the shared trigger table specified in the Engineering Design — it cannot be a column bolted onto each concern’s own table without leaving silent holes in the ones that get missed.
