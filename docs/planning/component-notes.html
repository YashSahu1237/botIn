Yesmadam · Partner Experience · R&D Ladder, Step 6

Component Notes

One page per library the design depends on — what it does, how it is wired, and what actually surprised us when we ran it. Written from spike evidence, not documentation.

This document is the deliverable of the entire R&D ladder. The spike project was a way of asking questions; these pages are the answers. Once they are written the project gets deleted, and nothing is lost.

Two things make it worth the hour. Writing a page is how you find out you do not understand something — the gaps are invisible while the tests are green and obvious the moment you try to explain the mechanism. And these pages become the first draft of the production runbook and of whatever the next person reads before touching this system.

Edit it. Everything below is drafted from what the spikes showed, but the understanding being recorded is yours. Where a sentence does not match what you actually learned, change it — a note you would not have written yourself is worth very little six months from now.

1Flowable process engine

BPMNOrchestration — the thing that remembersProven
What it does
Runs a conversation described in an XML file. T0, T1 and T2 could all be plain Java — request in, response out. T3 cannot. It stops at "waiting for a human" and must resume hours later, across deploys and crashes, without losing its place. That single requirement is the reason the engine exists in this design.
How it is wired

One Maven dependency, flowable-spring-boot-starter. On boot it creates roughly 25 ACT_* tables and scans src/main/resources/processes/*.bpmn20.xml.

A delegate is a Spring bean with one method. The BPMN names it — flowable:delegateExpression="${logDelegate}" — and the engine looks it up by bean name. That string plus the @Component name is the entire wiring; there is no registration step.

A User Task writes a row to ACT_RU_TASK and returns. No thread is blocked and nothing is held in memory.

What we proved
Started a process, parked it on a User Task, tore the Spring context down entirely, and started a fresh one that had never seen the instance. The same task id came back, completed, and the process ran to its end event.
What surprised us

ACT_RU_* rows are deleted when a process completes — "RU" is runtime, "HI" is history. So anything the caller needs after completion cannot be read from process variables; they are gone.

That is not a detail, it is a design constraint: it is precisely why the final Service Task writes nextStep onto the help_session row instead, and why Layer 1 re-reads it from there.

Watch in production
Async job executor configuration for multiple pods · dead-letter job monitoring · in-flight instances stay pinned to the process version they started on across a deploy · history-level stays audit, never full.

2Flowable DMN engine

DMNDecisions — the thing that does not rememberProven
What it does
Evaluates a grid of conditions and outcomes. Facts in, {tier, action} out. Stateless, synchronous, sub-millisecond. The sharp contrast with the process engine: the process engine remembers, the decision engine does not.
How it is wired

Ships in the same flowable-spring-boot-starter — we added no dependency for it. Files live in src/main/resources/dmn/ and auto-deploy on boot.

<inputExpression><text>category</text></inputExpression> reads a process variable named category. That one line is the entire join between the two engines.

Called from Java through DmnDecisionService.createExecuteDecisionBuilder().decisionKey(...).variables(...).executeWithSingleResult(), or from BPMN by a single Business Rule Task.

What we proved
Three near-identical tables. The correct one returned auto_waive; the one with the catch-all moved to the top returned route_agent_catchall from identical rules and identical facts. Row order is logic, not formatting.
What surprised us

A table with no catch-all returns null. Not a default, not an exception — nothing. In a real process the gateway reading ${tier} then has no branch to take.

Thirteen of the 38 concerns in the mapping are currently written without a catch-all. Every table needs a terminal row added before it is deployed.

Watch in production
A terminal catch-all on every table · who may edit a table that moves money, and whether that needs a review gate (decision D-3) · decision-table versioning, and whether in-flight pinning applies as it does to BPMN.

3Spring transaction propagation

REQUIRES_NEWThe most load-bearing line in the designProven
The problem
A Flowable Service Task runs inside the engine's transaction. Record the attempt, call the payment system, and if any later node throws, the engine rolls back — taking our record with it. The payment system does not roll back. Money has left and the database says nothing happened.
How it is wired
@Transactional(propagation = Propagation.REQUIRES_NEW) on recordAttempt(). Spring suspends the engine's transaction, opens a fresh one, writes the ATTEMPTED row, commits, and returns. Only then is the external call made.
What we proved
Recorded an attempt, threw from a later node, and the row survived the rollback. Then ran it again without the annotation and the row was lost.
What surprised us

The failing test matters more than the passing one. A test that only proves the good case cannot tell you whether it would catch the annotation being deleted later. Both directions, always.

And the trap that will reintroduce this bug: self-invocation silently disables @Transactional. Spring applies it through a proxy, so a call from inside AttemptRecorder to another of its own methods ignores it entirely — no error, no warning. The delegate calling the service from outside is what makes it work.

Watch in production
Re-test the moment the second datasource lands. The real service reads from a replica as well as its own schema, and a second datasource changes which transaction manager Spring selects. A wrongly wired one breaks this with no error at all.

4Togglz

FEATURE FLAGSThe kill switch — and the hole in itProven, with a caveat
What it does
Closes the gap between noticing money is moving wrongly and stopping it. Via revert-rebuild-redeploy that gap is fifteen to thirty minutes of continued wrong payments. With a flag it is seconds.
How it is wired

A library, no server. Three pieces: a Feature enum, a JDBCStateRepository holding state in the application database, and a console at /togglz-console. The console is what lets ops flip a switch rather than a developer.

Checked after the decision table returns auto-approve and before the action executor runs.

Critical semantic: flag off does not mean fail. It means do not automate, send to a human. The partner is still served.

What we proved
A flag flipped at runtime changed behaviour on the very next call with no restart. Resolving by NamedFeature string — which is what concern_catalogue.togglz_flag will hand us — agreed with resolving by enum constant.
What surprised us

A misspelt flag name does not throw. It reads as "off".

Combined with fail-to-human semantics, one typo in concern_catalogue would silently route an entire concern to human agents. No exception, nothing in the logs, and the only symptom is an agent-connect rate drifting upward for reasons nobody can trace.

Startup validation asserting every togglz_flag maps to a declared feature is therefore mandatory, not advisory. This is now evidence rather than caution.

Watch in production
JDBCStateRepository stores current state and nothing else — not who flipped a flag, nor when. Flip auditing has to be added. The console must be authenticated before Wave 1 (D-7). Cache TTL and a flag lifecycle policy both still need deciding.

5Resilience4j

CIRCUIT BREAKERDegrade to a human, never breakProven
What it does
Stops a failing dependency from becoming a failing product. When the Python classifier is down, the partner should get a human — not an error, and not a long wait.
How it is wired
@CircuitBreaker(name = "classifier", fallbackMethod = "degradeToAgent"), configured in application.yml. The fallback takes the same arguments plus a Throwable, must be public, and must not throw. Needs spring-boot-starter-aop on the classpath — the annotation does nothing without it.
What we proved
Four failing calls filled the window and the circuit opened. Every call returned T3; the caller never saw an exception.
What surprised us

Once the circuit is OPEN, the method body stops executing at all. The failure count stops rising, because there are no more attempts to fail.

That is what makes degradation cheap rather than merely graceful: a struggling dependency stops costing a three-second timeout on every single request. Without it, "degrades to a human" would still mean every partner waits three seconds first.

Watch in production
Tune the window and threshold against real classifier latency, not guesses · when the circuit opens the agent-connect rate rises, so it needs an alert · half-open behaviour on recovery.

6Flyway, alongside Flowable

MIGRATIONSTwo tools, one databaseProven
The question
Flyway wants to own the schema. Flowable creates its own ~25 tables through its own mechanism. If they fight, the service cannot use both — and every other spike result stops mattering.
How it is wired
Flyway owns our tables from db/migration/V*.sql. Flowable manages only ACT_*, through flowable.database-schema-update, and knows nothing about Flyway. They never look at each other's tables.
What we proved
With ddl-auto: none — so Hibernate could not have created anything — our tables existed, the entity mapped to them cleanly, and Flowable's tables sat alongside untouched. They coexist.
What surprised us

The only failure in the whole ladder, and it was our test rather than the tools. On H2, Flyway creates its history table with quoted lowercase identifiers — "flyway_schema_history" — while H2 folds an unquoted reference to upper case. So the obvious query looks for FLYWAY_SCHEMA_HISTORY and finds nothing.

Worth remembering generally: a BadSqlGrammar on a table you are certain exists is usually a quoting or case question, not a missing table.

Watch in production
Moving into empapi means baselining against a schema that already exists · migration ordering relative to Flowable's own startup DDL · never let ddl-auto creep back above validate.

7FastAPI and Pydantic

CLASSIFIERThe boundary that makes misclassification survivableProven
What it does
Turns free text into one value from a fixed list. Nothing else. No database credentials, no ability to take an action — which is what makes a wrong answer a routing error rather than a money error.
How it is wired

Two endpoints. Pydantic models with closed enums and Field(ge=0.0, le=1.0) on confidence. A validation failure becomes 502, not 500 — the fault is upstream — and Java's ClassifierClient treats any non-2xx identically: set tier = T3 and carry on.

The error body is structurally unlike a result: no category, no confidence_score. Nothing downstream can mistake one for the other.

What we proved
A hallucinated category, a confidence of 1.7, a missing field, an unknown language and prose instead of JSON were all rejected at the boundary. A confident "I don't know" was correctly accepted — low confidence is a valid answer, and Java's threshold decides what to do with it.
What surprised us

"Be liberal in what you accept" is only half right here, and the half that is wrong costs money.

A model returning " r9_no_product " with stray spaces and wrong case is sloppiness — normalise it. A model returning refund_immediately is a different thing entirely. Liberal about formatting, strict about membership. That distinction is one validator, and getting it backwards in either direction causes real problems: too strict and you reject good answers over whitespace, too loose and a hallucination reaches a decision table.

Also worth internalising: 1.7 would have passed every >= 0.7 rule in every table we will ever write.

Watch in production
Swapping the stub for a vendor touches one file — keep the bad-response fixtures, they are how you find out a new vendor breaks the contract differently · partner free text may contain personal data, so the PII position must be settled before any of it leaves the network · timeout tuning against real vendor latency.

Three caveats apply to everything above. All of it ran on H2, not Postgres — re-run before treating any of it as final. And REQUIRES_NEW has not been tested with two datasources, which is the configuration the real service will have.

Then delete the spike project

It has served its purpose. It has an H2 file database, mock everything, and a controller whose only reason to exist was letting you kill -9 it. Keeping it around invites someone to copy from it.
