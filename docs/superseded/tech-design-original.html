What changed this pass

v0.1: confirmed Java backend, picked Flowable for orchestration, pulled real sourced detail from Swiggy's published architecture. v0.2: split the stack explicitly — Java owns all data access and actions (queries, wallet/leave/hub/booking calls, orchestration); Python owns only the AI-touching surface (the two narrow LLM calls), talking to each other over one small REST contract. Diagram and Layer 5 rewritten below to make that boundary concrete rather than leaving "Python does AI" vague.

Terminology — the acronyms used throughout this document

Term Full form What it is
BPMN Business Process Model and Notation An OMG specification for describing a process — the sequence of steps, branches, waits and hand-offs. Renders as a flowchart; the XML is directly executable by an engine. Layer 3.
DMN Decision Model and Notation An OMG specification for describing a decision — a table of input conditions mapped to outputs. Layer 4.
CMMN Case Management Model and Notation The third OMG sibling, for unordered ad-hoc work. Not used in this design.
OMG Object Management Group The standards body behind all three — and behind UML.

The naming parallel between BPMN and DMN is deliberate: one notates processes, the other notates decisions. Both are specifications, not software. Flowable is the product that executes them, and it ships a separate engine for each — which is why Layer 3 and Layer 4 need only one dependency between them.

Other acronyms in use: SP (Service Partner), CTI (Computer Telephony Integration — the screen-pop link between a phone call and an agent's screen, Layer 8), LLM (Large Language Model, Layer 5), RAG (Retrieval-Augmented Generation — not used in this design, see Layer 13).

Layer 1 — Client integration (the part you'll finalize with frontend)

The pattern, regardless of exact JSON shape you settle on: this is a server-driven conversational state machine, not a generic chat API. The client never decides what to show next — it renders whatever the backend's current session state says (a menu of L1 options, an order dropdown, a free-text box for a dispute reason, a resolution message, a CSAT prompt). Concretely, that means at minimum three endpoints: one to start a Help session (POST /help/sessions), one to submit the SP's input for the current step (POST /help/sessions/{id}/input), and one to fetch current state (GET /help/sessions/{id}) — useful for reconnect-after-app-restart. Each response carries a nextStep descriptor (type: menu / dropdown / text / message / csat, plus its options/content) so the client is a thin renderer, not a second copy of the flow logic. This is deliberately left light here since you and frontend own the exact contract — but the "backend owns 100% of the flow logic, client only renders" boundary is the actual design decision worth locking in early, since the alternative (client encodes any flow logic) means the flow lives in two places and drifts.

Entry with no menu selection at all. The SP can open Help and type free text as the very first message instead of tapping an L1 option — e.g. "mera aaj strike laga hai usko hatao." That POST /help/sessions call arrives with freeText set and both l1Concern/l2Concern null. Java cannot start a Flowable process yet, because a process is picked by name (startProcessInstanceByKey("<l2-concern>", ...)) and there's no category to pick from. This is not covered by Layer 5's /classify service — that endpoint is only ever given a concern it already knows and asked to extract a reason within it. Unconstrained entry text needs a separate, broader step first — see the new Layer 5b below — before anything else in this document applies. This path exists for real (it's the industry-standard "free text as fallback, not just the front door" pattern), so it isn't an edge case to defer; it's a distinct entry branch every session has to check for.

Layer 2 — Session/Ticket state (the backbone)

Two distinct entities, not one, because a Help interaction exists before a ticket does (per the BRD's "No gate — T0" case):

HelpSession — created the instant the SP taps Help. Fields: id, spId, currentStep, l1Concern, l2Concern, selectedBookingId (nullable), startedAt. Lives and dies within one interaction; if it resolves at T0 (pure deflect), no Ticket is ever created — this is Gate 1 from the BRD, made literal: a Ticket row only gets inserted the moment an L2 concern is selected that needs an answer or action.

Ticket — created at Gate 1. Fields: id, helpSessionId, l1, l2, l3 (once you've written the L3 rules), tier (T0–T3), bookingId, status, agentOwner (BOT or a human agent id), createdAt, closedAt, csatResult.

TicketAction — one row per actual backend action attempted (a wallet credit, a leave mark). Fields: id, ticketId, actionType, idempotencyKey (unique constraint — this is your dedupe-on-retry guarantee), status (pending/succeeded/failed), requestPayload, responsePayload, attemptedAt. This table is also your audit log and your reconciliation job's source of truth — it doesn't need to be a separate system.

ConversationMessage — one row per turn, written continuously by the Java API layer on every POST /help/sessions/{id}/input and every response sent back, regardless of tier and regardless of whether the session ever escalates. Fields: id, helpSessionId, ticketId (nullable until Gate 1), sender (SP/BOT), content, stepType, timestamp. This is the raw transcript — kept, but deliberately not the first thing an agent sees (see Layer 8).

EscalationContext — one row per ticket that actually escalates, written once by the "Assemble Escalation Context" step at the moment a T3 trigger fires (Layer 10). Fields: ticketId, category, confidenceScore, extractedReason (the plain-language reason Layer 5/5b already pulled out of the SP's free text — this is the "gist," already computed, not something built fresh for the agent), medalBand, recentTicketHistory (a short rollup reusing the same claim-frequency query Layer 4's DMN table already runs — e.g. "3 similar tickets in 30 days, 2 bot-resolved, 1 escalated"), priorTicketActions, triggerReason (which of the three T3 entries fired), createdAt. This is what the agent's screen loads first — computed facts, not a transcript.

Layer 3 — Orchestration: Flowable, embedded

Given Java + solo developer + wanting to avoid new paid infrastructure, Flowable embedded directly in your existing Spring Boot service is the concrete recommendation, not just "a BPMN engine" in the abstract. Concretely: Flowable ships as a Maven dependency (flowable-spring-boot-starter), runs inside your existing app's JVM, and persists its own process state into the same database you already run — no separate service to deploy, no new infrastructure, no license cost. You author each L2 concern as an actual BPMN diagram (using Flowable's free web modeler or the desktop Eclipse-based one) instead of hand-writing a state machine in Java — which is the direct answer to "every connection I need to understand": the diagram is the logic, and you can point at it and explain exactly what happens at each box.

Concretely, per L2 concern: one BPMN process definition, with Service Tasks calling your Action Executor beans (Flowable calls a Java class you write — a JavaDelegate — at each Service Task node), Gateways implementing the tier/trigger branching, and a User Task (assigned to a queue, e.g. agent-2-standard or agent-2-priority per medal band) for the T3 handoff — Flowable gives you task-queue semantics natively, so "route to Agent 2" is a real primitive, not something you build by hand.

Layer 4 — Decision logic: DMN, for the L3 rules specifically

The L3 "genuine case Yes/No" rules (the gap we identified in your Rough tab) become actual DMN decision tables — also free, also embedded in Flowable, also editable via a web modeler. Concretely: input columns (concern reason, claim frequency in last 30 days, order value), output column (auto-approve / needs-review / auto-deny). This is where you'd later graft in the claim-history scoring idea from the industry study, as an additional input column computed by a small Java service before the DMN table is evaluated — not as a wholesale LLM decision.

Layer 5 — The Python AI microservice (language understanding only, never the decision)

Grounded in Swiggy's own published approach now, not just inference: their system uses tiered model complexity — cheap/fast handling for simple cases, larger reasoning models reserved for genuinely hard ones — and explicitly moved away from letting one LLM make routing/assignment decisions end-to-end, because that only hit 90% accuracy; they got to higher accuracy by combining rule-based routing with a small, dedicated model for one narrow decision. Your architecture should draw the same boundary, made concrete: Python's job is strictly understanding language, never deciding the outcome. The actual business decision (auto-approve / needs-review / auto-deny) stays in Java's DMN table, which combines Python's output with other business inputs (claim frequency, order value) that Java computes from its own database. That split matters because the business rule is something ops will want to tune over time (via the DMN table), while the language-understanding model is something you'll want to swap or upgrade independently — coupling them would make either change risk breaking the other.

Concretely, the service: a small FastAPI app (genuinely small — a wrapper around one LLM API call plus a Pydantic schema for the response, not an ML infrastructure project), deployed as its own lightweight container — fits your existing Jenkins + Argo CD/EKS pipeline as one more small deployment, not a new platform. It's called from three places: the free-text fine-dispute-reason step, the low-confidence/fallback check (Trigger C) — both via /classify — and the entry-point intent router described next, via a second endpoint.

Layer 5b — Entry-point intent routing (/classify-intent): a distinct, broader job from /classify

/classify and /classify-intent are not the same task wearing two names — keep them mentally separate. /classify already knows the L2 concern (Java passes it in) and only extracts a reason within that one concern's fixed category set — e.g. is this fine dispute "health issue," "family emergency," or "other." /classify-intent gets called when Java has no concern at all yet — raw free text typed before any menu selection — and has to match it against your entire L1/L2 taxonomy (everything in the SOP tab), which is a materially bigger classification surface than any single concern's reason set. Treat it as its own endpoint on the same FastAPI app, not a mode flag on /classify, so each can be tuned (prompt, model, evaluation) independently as the taxonomy grows.

The contract:

POST /classify-intent
Request:  { "sessionId": "...", "freeText": "mera aaj strike laga hai usko hatao" }
Response: { "l1Concern": "Strike", "l2Concern": "Strike appeal", "confidenceScore": 0.95 }

What Java does with the result: on confidence above threshold, Java back-fills the HelpSession's l1Concern/l2Concern and starts the matching Flowable process exactly as if the SP had picked it from a menu — everything downstream (Layers 3–10) is identical from that point on, with one addition: whatever EscalationContext eventually gets built for this ticket should also carry the original free text, the matched category, and the confidence score, so a reader (agent or engineer) can see how the system arrived at that category, not just where it ended up.

On low confidence: an open policy choice, not yet decided. Two honest options exist — fall back to showing the L1 menu and asking the SP to pick manually, or route straight to a T3 human handoff tagged "unclassified free text." Either is workable; which one is a product call, not an architecture one, and nothing else in this design depends on the answer.

Implementation note, not a requirement: a cheap keyword/regex fast-path (e.g. "strike" → Strike appeal directly) before ever calling the LLM is a legitimate optimization here, in the same spirit as Swiggy's tiered-model-complexity pattern already cited in this layer — simple, unambiguous phrases don't need a model call at all. Worth doing once volume data shows which phrasings are common; not a blocker to building the LLM path first.

The contract, concretely — not "Python does AI":

POST /classify
Request:  { "ticketId": "...", "l2Concern": "Leaves fine", "freeText": "..." }
Response: { "category": "health_issue", "confidenceScore": 0.87, "extractedReason": "..." }

Java's JavaDelegate for that Service Task makes this call with a short timeout (e.g. 3s) and, on timeout, non-2xx, or confidence below your threshold, sets a process variable that routes the Gateway straight to the Agent-2 User Task — Trigger C, made literal, rather than blocking the ticket on a flaky external call. Worth wrapping the call in Resilience4j's circuit breaker (a standard Java library, works well with Spring) so a struggling Python service degrades to "route to human" automatically rather than piling up timeouts.

Why this split earns its keep, beyond "Python is good at AI": it means the Python service has zero database credentials and zero ability to take an action — it can misclassify, but it can never wrongly credit a wallet, because it structurally can't reach the wallet. That's a real safety property, not just a tidy architecture diagram.

Layer 6 — Action Executors / integration adapters

One Java interface per capability, e.g. WalletActionService.creditTransport(spId, orderId, amount, idempotencyKey), LeaveActionService.markLeave(...), HubActionService.addHub(...). Each interface has exactly one implementation for now, which either calls an existing REST endpoint on empapi/app_server (if it exists) or the direct service-layer call if you're in the same codebase — the interface boundary means this decision is invisible to everything above it. Whether those endpoints already exist is a real open question (audit empapi/app_server/admin for it), but it's not gating anything else in this design — the interface abstraction is exactly what lets every other layer be designed independently of the answer. Pick this up whenever it's next in your own sequence.

Layer 7 — Safety: idempotency, reconciliation, kill switches

Idempotency: the unique constraint on TicketAction.idempotencyKey already described — generate it as a hash of (ticketId, actionType), so a retried call is a no-op, not a double-credit. Reconciliation: a Spring @Scheduled job, running daily, that sums TicketAction credits per SP against the actual wallet ledger and flags mismatches — this can be a plain cron-annotated method, no new infrastructure. Kill switches: Togglz — a Java-native, Spring-integrated, free feature-flag library, purpose-built for exactly "flip this flow off instantly without a redeploy." One flag per L2 concern going live is the right granularity.

Layer 8 — Agent-connect (T3)

When a Gateway routes to the User Task for Agent 2: a Java call to Exotel's (or Ozonetel's) outbound-call REST API, triggering the call, passing only the ticketId as call metadata — not the context itself, just enough for the screen-pop.

What "the whole context" actually means, made concrete — two calls, not one, and not equal weight:

  1. GET /tickets/{id}/escalation-context — the agent's screen calls this first, before the call even connects. Returns the EscalationContext row (Layer 2): category, confidence, the already-extracted plain-language reason, medal band, recent-ticket-history rollup, prior actions, and which trigger fired. This is computed facts, not a chat log — matching the industry pattern of showing an agent what happened, not a transcript to re-read.
  2. GET /tickets/{id}/conversation — a second, separate endpoint, called lazily (behind a "view full conversation" control on the agent's screen, not auto-loaded). Java queries ConversationMessage (Layer 2) by ticketId/helpSessionId, ordered by timestamp, and returns the full turn-by-turn SP↔bot exchange. This exists for the cases where the structured summary genuinely isn't enough — but it's secondary by design, not the primary view.

Deliberately not built here: an LLM call to generate a prose summary of the conversation for the agent. EscalationContext.extractedReason already is the summary — structured, not prose — reused from the classification step that already ran. Adding a third LLM touchpoint just to re-summarize what's already been extracted would be scope creep, not a missing piece; revisit only if real agent usage shows the structured view genuinely isn't enough.

Whether the destination for either endpoint is your existing ticketing/CRM tool (if it has a way to embed this) or a small purpose-built screen is still open — worth confirming what agents currently look at today before deciding. That choice doesn't change either endpoint's contract above.

Layer 9 — Observability

Micrometer (Java's standard metrics facade, works natively with Spring Boot) instrumented at each layer, exported via the OpenTelemetry Java agent, into Prometheus + Grafana if self-hosting (free), or whatever Yesmadam's EKS cluster already runs for app_server/admin (worth checking — you may already have this for free). Dashboard the same numbers the BRD itself defines as KPIs: automation rate, agent-connect rate, reconciliation accuracy, CSAT — plus, borrowing directly from Swiggy's real pattern, explicit alert thresholds (e.g., alert if agent-connect rate exceeds 20% or reconciliation mismatch > 0) rather than a dashboard nobody's watching.

Layer 10 — Illustrative end-to-end flows, T0 through T3 (client request → client response)

Every step below names one block, and says what it receives, what it does, and what it sends onward — so every arrow in the architecture diagram has a real request/response behind it, not just a label.

T0 — "How do I update my bank details" (pure deflect)

  1. SP App — Receives: n/a (start). Does: SP selects a fixed menu option. Sends: POST /help/sessions/{id}/input {selectedOption} → Java API layer.
  2. Java API layer — Receives: that request. Does: creates a HelpSession only (no Ticket); matches the option against a static canned-answer list — no Flowable, no DMN, no Python, since there's no branching to model. Sends: composes the response itself.
  3. Java API layer → SP App — Sends: {nextStep: {type: "message", content, ctaLink}}.
  4. SP App — Receives/renders it. Result: session closes; no Ticket, no TicketAction, nothing for reconciliation to see.

T1 — "Why was my rule-break fine deducted" (bot answers, ticket exists, nothing changed)

  1. SP App — Selects "Rule-break fine" → "Why was this deducted." Sends {l2Concern, subIntent: "explain_reason"} → Java.
  2. Java API layer — Receives that. Creates HelpSession. Recognizes this needs a real per-SP decision, not a canned answer. Sends: Flowable.startProcessInstanceByKey("fine-query-informational", {l2Concern, spId, fineId}).
  3. Flowable — Receives the start call. Begins the BPMN diagram; first node is a Business Rule Task. Sends: calls the DMN table with {l2Concern, requestType: "informational"}.
  4. DMN table — Receives those inputs. Matches its rule row → {tier: T1, action: explain-reason}. Sends: that result back to Flowable.
  5. Flowable — Receives it. T1 means "needs a real answer" — this is Gate 1, so it calls back into Java to insert the Ticket row. Moves to a Service Task. Sends: invokes JavaDelegate FineReasonLookupDelegate.execute(fineId).
  6. Java (JavaDelegate) — Receives fineId. Queries the fines table for the reason code. Sends: returns it to Flowable.
  7. Flowable — Receives the reason code. Fills a fixed message template (plain templating, not an LLM — fixed reason-code set). Marks Ticket.status = Bot Resolved. Ends the process. Sends: the message up through Java's API layer.
  8. SP App — Receives/renders it. Result: Ticket exists for reporting; no TicketAction — nothing was changed, only explained.

T2 — "I was sick yesterday, please waive my leave fine" (bot takes a real action)

  1. SP App — Selects "Leaves fine," types free text (free text specifically because the reason can't come from a fixed menu). Sends {l2Concern, freeText} → Java.
  2. Java API layer — Creates/updates HelpSession. Sends: Flowable.startProcessInstanceByKey("leave-fine-dispute", {spId, l2Concern, freeText}).
  3. Flowable — Receives the start call. First node is a Service Task built for this free-text step. Sends: POST /classify {ticketId, l2Concern, freeText} to Python, behind a Resilience4j circuit breaker with a 3s timeout (both configured Java-side).
  4. Python (/classify) — Receives that request. Builds a prompt, calls the LLM API, parses into a fixed schema. Sends: {category: health_issue, confidenceScore: 0.91, extractedReason: "sick leave"} back to Flowable.
  5. Flowable — Receives the classification. Next node is a Business Rule Task. Sends: calls DMN with {category, confidenceScore, claimFrequencyLast30Days, medalBand} — the last two fetched by Java from the DB just before this call.
  6. DMN table — Receives those four inputs. High confidence, recognized category, low claim frequency → matches "auto-approve." Sends: {tier: T2, action: waive_fine} back to Flowable.
  7. Flowable — Receives that. Confirms the Ticket with tier=T2. Before acting, next Service Task checks the kill switch. Sends: calls Togglz.isActive("leave-fine-auto-waive") — an in-process call, no network hop.
  8. Togglz — Receives that check. Looks up the flag. Sends: returns true to Flowable.
  9. Flowable — Receives true. Proceeds to the real action. Sends: calls FineActionService.waiveLeaveFine(spId, fineId, idempotencyKey).
  10. Java (Action Executor) — Receives that call. In strict order: writes a TicketAction row (ATTEMPTED + idempotency key) → calls the downstream fines system → flips the row to SUCCEEDED. Sends: returns success to Flowable.
  11. Flowable — Receives success. Marks Ticket.status = Bot Resolved/T2. Ends the process. Sends: confirmation message up through Java's API layer.
  12. SP App — Receives/renders "Your leave fine has been waived." Result: tonight's reconciliation job checks this TicketAction against the real ledger; every step 3–11 left an OTel trace span.

T3 — agent connect (three entries, one shared path after)

Entry A (Trigger C, low confidence): identical to T2 steps 1–5, except Python returns confidenceScore: 0.42 in step 4. In step 6, DMN's rows don't match "auto-approve" at that confidence — a fallback row matches instead, returning {tier: T3, action: route-to-agent}. No Action Executor is ever called.

Entry B (Trigger A, dissatisfaction): T2's full flow already completed. SP taps an explicit "talk to a human" button (assumed a UI action, not inferred from free text — still open). Sends {action: request_human} → Java, which signals the ticket's Flowable process into the shared path below.

Entry C (unconstrained free text at Help entry, no menu selection — e.g. "mera aaj strike laga hai usko hatao"): 1. SP App — Does: types free text as the first message, no L1/L2 selected. Sends: POST /help/sessions {freeText} → Java. 2. Java API layer — Receives that. Creates HelpSession with l1Concern/l2Concern null — can't pick a Flowable process by name yet. Sends: POST /classify-intent {sessionId, freeText} → Python (see Layer 5b). 3. Python (/classify-intent) — Receives raw text, no category hint. Matches against the full L1/L2 taxonomy. Sends: {l1Concern: "Strike", l2Concern: "Strike appeal", confidenceScore: 0.95} back to Java. 4. Java — Receives that. Confidence is above threshold, so it back-fills the HelpSession's category fields and proceeds as if the SP had picked this from a menu. Sends: Flowable.startProcessInstanceByKey("strike-appeal", {spId, l2Concern: "Strike appeal"}). 5. Flowable — Receives the start call. Strike is Wave 4 — human-owned by design, not automated — so this process has no DMN auto-approve/deny branch at all; its one meaningful node is a Gateway that routes straight into the shared T3 path below. Sends: same as steps A–C below, except the EscalationContext payload also carries the original free text, the matched category, and the confidence score, so the agent (or anyone reading this later) can see how the system arrived at "Strike," not just that it did.

(On low confidence at step 3 instead: Java either falls back to showing the L1 menu and asks the SP to pick manually, or routes straight into the shared T3 path tagged "unclassified free text" — see Layer 5b for why this choice isn't locked yet.)

From any of the three entries: - A. Flowable — Receives the tier=T3 decision (or signal). Routes to a Service Task. Sends: calls EscalationContextBuilder.build(ticketId). - B. Java (EscalationContextBuilder) — Receives ticketId. Queries the Ticket, classify result if any (including extractedReason), medal band, prior TicketActions, and a recent-history rollup (reusing Layer 4's claim-frequency query); assembles one EscalationContext row (schema in Layer 2). Sends: writes it, keyed by ticketId — this single write is the "context save." The full ConversationMessage transcript is not re-packaged here — it already exists continuously (Layer 2) and the agent's screen fetches it separately, only if asked for (Layer 8). - C. Flowable — Receives confirmation it saved. Next Service Task calls telephony. Sends: POST to Exotel/Ozonetel with {ticketId, spPhoneNumber} — just enough to route the call, not the context itself. - D. Exotel/Ozonetel — Receives that request. Places/queues the call; on connect, passes ticketId as call metadata (the screen-pop). Sends: nothing back into your system yet. - E. Flowable — Reaches a User Task on an agent queue (e.g. agent-2-priority for a Titanium SP) and waits. - F. Agent's screen (existing admin panel) — Receives ticketId from the screen-pop. Sends: GET /tickets/{id}/escalation-context → Java. - G. Java API layer — Receives that GET. Looks up the row from step B. Sends: returns it as JSON. - H. Agent's screen — Receives the JSON. Renders it as a case summary. Result: agent resolves the issue in the existing admin system, outside this flow. - I. Existing admin system → Flowable — Some mechanism (webhook or polling job — still open, Layer 8) tells the waiting User Task the ticket closed. Sends: completes the User Task. - J. Flowable — Marks Ticket.status = Agent Resolved, ends the process. SP App's "connecting you..." state updates to "resolved."

Layer 11 — Access control / permissions (PLACEHOLDER — not yet designed)

Why this exists, concretely, not abstractly: Layer 8's two agent-facing endpoints (GET /tickets/{id}/escalation-context and GET /tickets/{id}/conversation) return an SP's health reason (e.g. extractedReason: "sick leave"), financial actions, and full chat history. Nothing in the design today says which agents can call these for which tickets, or logs who did. Sourced from re-reading Swiggy's own architecture (their "AI Gateway" centralizes permissions and rate limits for anything touching the agent) — this is the one piece of their stack we have no equivalent of at all.

Not yet decided: whether this rides on an existing auth system (if the admin panel already has agent logins/roles) or needs its own; whether access should be scoped per-queue (e.g. an agent only sees tickets in their assigned medal-band queue) or open to any logged-in agent; whether viewing EscalationContext/ConversationMessage needs its own audit log distinct from TicketAction's. Pick this up whenever it's next in your sequence — flagged here so it's not silently missing from the doc, not because it blocks anything above it.

Layer 12 — LLM guardrails (PLACEHOLDER — not yet designed)

Why this exists, concretely: Python's response to /classify//classify-intent flows straight into Java's DMN table today with no validation — nothing checks that confidenceScore is actually between 0 and 1, that category is one of the values Java's DMN table actually recognizes, or that extractedReason isn't empty or garbled. Going the other direction, an SP's raw free text flows straight into an LLM prompt with no defense against text specifically crafted to manipulate the classifier's output. Since /classify's result can trigger real money movement in T2 (Layer 3's walk-through), this is a real risk surface, not a theoretical one. Sourced from the same re-read of Swiggy's architecture — their gateway explicitly "blocks unsafe, non-compliant, or harmful data at model endpoints."

Not yet decided: where this validation lives (a thin wrapper in Java right after the /classify call, before the result reaches Flowable's DMN task, is the natural place given Python has no DB access to enforce anything itself); whether "unrecognized category" should hard-fail to T3 (safe default) or retry once; whether free-text input needs any pre-filtering before it reaches the LLM at all, or whether a strict output-side check is sufficient given the narrow, closed-set nature of both endpoints.

Related, smaller, likely folds into Layer 9 rather than needing its own layer: LLM-specific evaluation — whether /classify's real-world accuracy is holding steady or drifting over time, which is a different question from Layer 9's uptime/latency observability or the BRD's business KPIs. Even a simple periodic sample-and-manually-review process would close this; not urgent enough to be its own layer at this scale.

Layer 13 — AI agents for the Wave 4 long tail (FUTURE, explicitly out of scope for Waves 1–3)

What an AI agent is, and why it's different from everything else in this document: every LLM call in this design so far (/classify, /classify-intent) is single-shot — one input, one call, one structured output, no ability to act. An AI agent is different in kind, not degree: it runs a loop — observe, decide on an action (often a tool call — check an order, look up a policy, issue a refund), act, observe the result, decide again — until it judges the task done. Uber's COTA (agent-assist, a human still decides) versus Intercom Fin (a true autonomous agent that decides and acts) is the same distinction in an already-cited real-world pair.

Why this is the right shape specifically for Wave 4's "Other any issue" bucket, and nowhere else in this design: that bucket is open-ended by definition — no fixed menu, no fixed BPMN diagram, no closed category set for a classifier to sort into. That's the same gap that made RAG a plausible future fit for this exact bucket (noted when RAG was first discussed) — an agent with retrieval (RAG, for grounding in real policy/SOP text) and a small set of safe tools is the natural real-world answer once you get there. It is not proposed for T0–T3: Swiggy's own sourced result (already driving the Java/Python split) is that one model deciding routing/action end-to-end capped out lower than hybrid rule-based routing plus a narrow model for one decision — an autonomous agent deciding tier and action itself is exactly the pattern that result argues against, and Python having zero ability to take actions (Layer 5) is a safety property a true agent would need to break by definition. For flows that move real fines and wallet credits, "DMN rule 4 fired" is a defensible answer to an SP dispute; "the agent decided" is not.

Not yet decided, and not urgent: nothing here is designed — this is a placeholder marking where an agent (and RAG) would go if Wave 4 is ever tackled, not a component to build now. When you do reach it: what tools it would be safely allowed to call (read-only lookups are far safer than anything action-shaped), what document corpus RAG would retrieve from, and whether it still reports into the same Ticket/TicketAction model or needs its own.
