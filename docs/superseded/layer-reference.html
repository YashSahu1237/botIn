Cross-cutting

Deployment View — where the code actually lives

The distinction this tab exists to fix

  • Layers are logical, not physical. "Layer 3 calls Layer 6" describes a dependency, not a network hop — most of those calls are ordinary Java method calls inside one process.
  • We build exactly two deployables. Everything else is either a vendor (Exotel) or an existing Yesmadam system.
  • Layers 1, 2, 3, 4, 6, 7, 8, 9 — and 11/12 when built — are all one Spring Boot process. Flowable, its DMN engine, and Togglz are libraries inside it, not services.
  • Only Layers 5 and 5b live somewhere else: the Python classifier. That's the single process boundary inside our own system.
  • Which existing app hosts that Spring Boot process is a pending team decision — see the last section. It is not app_server: that one is customer-facing, and BOTIn serves Service Providers.

Layer 1

Client Integration

In brief

  • A server-driven conversational state machine, not a generic chat API — the client never decides what to show next, it only renders.
  • Three endpoints cover it: POST /help/sessions (start), POST /help/sessions/{id}/input (submit the SP's answer), GET /help/sessions/{id} (reconnect after an app restart).
  • Every response carries one nextStep descriptor — a type plus its content/options — so the client is a thin renderer, never a second copy of the flow logic.
  • One entry variant breaks the pattern on purpose: the SP can type free text as the very first message, before any menu selection — that request carries no l1Concern/l2Concern at all, and forks into Layer 5b before anything else applies.

Pros & cons

Pros

  • One contract for all four tiers — the client never forks its own logic per tier, it only renders whatever nextStep says.
  • Decouples app release cycles from flow changes — a new BPMN diagram or a DMN rule change never needs an app store update.
  • Clean reconnect story: GET /help/sessions/{id} rebuilds the exact same screen after a crash or app restart.

Cons

  • Every new step type needs client-side rendering support shipped before the backend can rely on it — a real coordination cost with frontend.
  • Fully thin-client means zero offline capability — every step needs connectivity, even a T0 deflect.
  • The free-text-first entry path (Layer 5b) still needs a UX decision — does the client always show a text box alongside the menu, or only as a fallback link?

R&D for scale / efficiency

  • At higher T3 volume, swap client polling of GET /help/sessions/{id} for a push channel (WebSocket or SSE) so "agent resolved" arrives instantly instead of on the next poll.
  • Add a client-generated idempotency key on POST .../input so a dropped connection and a client retry can't double-submit the same step.
  • Template localization: the SOP already mixes Hindi/Hinglish free text (the "strike" example) — message content will need multi-language templates before Wave 2+, not just English.

Layer 2

Session/Ticket State

What this layer is, and what it does

  • It is not a service — it's a package inside the existing Spring Boot app, sharing one DataSource with Flowable's own tables. Nothing new to deploy.
  • Its actual job is owning every write to the five entities, and enforcing when and in which transaction each write happens — the tables are the easy part; the transaction boundaries are the design.
  • Gate 1 lives here: a Ticket row is only inserted once a concern needs a real answer or action. Pure deflects never create one.
  • It classifies its own writes by criticality — three are synchronous and must not be lost, one is deferrable and written off the request thread.
  • It is the single enforcement point for idempotency (TicketAction.idempotencyKey) — the thing that makes a retried action a no-op instead of a double credit.

Where it lives in the codebase

Who touches this layer, and why

API surface — none of it is HTTP

  • This layer exposes zero HTTP endpoints. Every SP-facing endpoint belongs to Layer 1; every agent-facing endpoint belongs to Layer 8. Layer 2 supplies the data behind them, nothing more.
  • What it exposes instead is a set of in-process Java interfaces — plain method calls inside the same JVM: no serialization, no network, no timeout or retry handling needed at this boundary.
  • It also makes zero outbound calls — it talks only to the database. That makes it a leaf: it can never be the source of a timeout, a circuit-breaker trip, or a cascading failure. Same kind of absolute boundary as "Python has no DB access."

Write paths — by criticality, not uniformly

The core design decision in this layer: which writes can wait
WriteSynchronous?Why
HelpSession create/updateYesThe next request reads it to know which step the SP is on
Ticket create (Gate 1)YesFlowable's process instance is keyed to it
TicketActionYes — and in its own transactionIt's the money record; see the transaction section below
ConversationMessageNo — deferredNothing in the flow ever reads it during the flow; only the agent screen, later, on demand
EscalationContextYesThe agent screen may load within a second of the write
  • How the deferred write works, without new infrastructure: publish a Spring ApplicationEvent during the request; consume it with @TransactionalEventListener(phase = AFTER_COMMIT) + @Async on a small bounded pool. The write lands off the request thread, after the main transaction commits.
  • The honest trade-off: if the JVM dies between commit and the async write, one transcript line is lost. Acceptable precisely because ConversationMessage is not the decision record — TicketAction is, and that one stays synchronous. The same trade would be unacceptable for the money table.
  • Why not a real queue (Kafka/SQS): it would close that gap, but it adds infrastructure to buy durability for the one table that needs it least. Revisit only if transcript completeness becomes a compliance requirement.

Transaction boundaries — the real hazard

  • Flowable is embedded and shares the DataSource, so a JavaDelegate runs inside Flowable's transaction by default. On the T2 path that creates a genuine failure mode.
  • The hazard, concretely: Flowable txn opens → write TicketAction(ATTEMPTED) → call the downstream fines API (money moves here) → write SUCCEEDED → a later step throws → Flowable rolls back and erases both rows. The credit happened in the real world with zero record of it — invisible to reconciliation.
  • The fix: the ATTEMPTED write runs in its own transaction (@Transactional(propagation = REQUIRES_NEW)) and commits before the external call. Everything downstream can roll back; the record survives and reconciliation catches the orphan.
  • This is also what makes the idempotency key work at all — a retry finds the committed row and refuses to double-credit. Without the separate transaction, the key protects nothing.

Pros & cons

Pros

  • No new deployable — one package, one DataSource shared with Flowable, which is what makes cross-boundary transaction control possible at all.
  • Splitting writes by criticality means the highest-volume write (transcript) costs nothing on the request path, while the money write keeps full durability.
  • REQUIRES_NEW on the action record makes idempotency and reconciliation actually load-bearing rather than decorative.
  • T0's deflects never touch Ticket at all — ops reporting and SLA metrics stay clean, not diluted by pure informational taps.
  • TicketAction doing three jobs at once (idempotency/audit/reconciliation) is one less table to build and keep consistent.

Cons

  • Mixed transaction propagation is subtle code — REQUIRES_NEW in the wrong place silently breaks either atomicity or the orphan-record guarantee, and it won't fail loudly in testing.
  • The deferred transcript write can lose a line on a hard crash; acceptable here, but it's a real (if small) gap someone will eventually ask about.
  • Sharing a DataSource with Flowable means its tables and yours grow in the same database — one noisy neighbour, one backup/restore surface.
  • Five tables now, likely more later (Layer 11's audit log is a strong candidate for a sixth) — entity sprawl risk without a periodic "can we merge any of these" check.
  • No schema-versioning story — a new DMN input field tomorrow means old Ticket rows simply won't have it.

R&D for scale / efficiency

  • Index before launch, not after: Layer 4's claim-frequency check is on the critical path of every T2 decision and Layer 8's recentTicketHistory rollup reuses it — an index on Ticket(spId, createdAt) is needed before Wave 1 goes live.
  • Prove the rollback case deliberately: write an integration test that forces a Flowable rollback after a simulated successful external call, and assert the TicketAction row survives. This is the one behaviour in this layer that silently regresses.
  • Tune the async pool with a bounded queue and an explicit rejection policy — an unbounded pool under load turns a deferred transcript write into a memory leak. Decide what happens when it's full: drop and log, or fall back to synchronous.
  • Retention/archival: HelpSession and ConversationMessage are the highest-write-volume, lowest-value-per-row tables — plan partitioning or cold-storage archival (e.g. older than 90 days) before real traffic forces it.
  • PII policy: ConversationMessage stores raw free text that can include health and financial details — the same sensitivity flagged in Layers 11/12, so decide its retention/redaction policy alongside those two rather than separately.
  • Partitioning trigger: Layer 7's nightly full-scan of TicketAction is the read that degrades first — monthly partitioning is the natural answer once that job's runtime starts growing.

Layer 3

Orchestration — Flowable, Embedded

Start here — why a workflow engine at all

  • Here is T2 (waive a leave fine) in plain Java, no Flowable: classify(freeText) → dmnTable.evaluate(...) → fineService.waive(...) → return ok("waived"). That is completely fine. Four steps, ~1.5s, returns. T0, T1 and T2 genuinely do not need an engine.
  • T3 is where plain Java runs out. escalateToAgent() has to return — you can't hold an HTTP connection open — but the work isn't finished. An agent picks it up in twenty minutes, or tomorrow.
  • Which leaves five questions with no home: who remembers this ticket is parked at "waiting for an agent"? where is the queue agents pull from? when the agent finishes, what marks the Ticket resolved and updates the SP's app? what if the app restarts while it's waiting? what if the Exotel call fails — who retries it?
  • Answering those in plain Java means building a ticket_state column, an enum of steps, a switch on that enum, an agent task table, resume logic, retry logic, and a background thread to drive it. That collection of things is a workflow engine — Flowable is one that already exists and is already tested.
  • In one sentence: a Java library that runs multi-step processes which can pause, survive restarts, and resume later — where you describe the steps as a diagram instead of writing the state-tracking plumbing.

What "a Maven dependency" means here, concretely

  • You add org.flowable:flowable-spring-boot-starter to pom.xml. Same as adding Jackson or Lombok — a JAR that becomes part of your app. There is no Flowable server to install, no separate process, nothing to deploy. It runs inside your Spring Boot JVM.
  • On startup it does exactly three things: (1) creates ~25 tables in your existing database, all prefixed ACT_ — that's where paused processes live, and why a ticket survives a restart; (2) scans src/main/resources/processes/ for .bpmn20.xml files and loads them as process definitions; (3) registers a few Spring beans you can @Autowired.

  • The naming parallel is deliberate: BPMN notates processes, DMN notates decisions — same standards body (OMG, also behind UML), same XML-plus-diagram shape.   • What "engine" means in Java terms: not a server, not a process — an object. What BPMN is, and the four shapes we use

  • An XML format for describing a process, which renders as a flowchart. You edit it in a visual modeler, it saves as XML, and the XML is executable — not a picture of the code, the code itself.

The Java you actually write

  • For each Service Task, one Spring bean. It implements JavaDelegate, which has a single method: execute(DelegateExecution execution). Inside it you read variables, call your own services (fineService.waive(...)), and set a result variable. That's the whole contract.
  • The BPMN box points at it with flowable:delegateExpression="${waiveFineDelegate}" — matching the Spring bean name. That single attribute is the entire wiring between diagram and code.
  • Process variables are the other core concept: a Map<String,Object> that travels with the instance and is persisted to the database. It's how step 3 sees what step 1 produced. Keep it small — IDs and flags, never blobs.

What happens at runtime, step by step

  • 1. Layer 1 calls runtimeService.startProcessInstanceByKey("leave-fine", {spId, fineId, freeText}).
  • 2. Flowable writes a row to ACT_RU_EXECUTION: instance #4471, at node "Classify".
  • 3. It calls classifyDelegate.execute(...) — your code, on the current thread.
  • 4. Moves to the gateway, reads the confidence variable, follows the "yes" arrow, updates the row: now at "Evaluate DMN".
  • 5. …and so on, until it either hits an End Event (row deleted, process done) or a User Task (row stays: #4471 parked at "Wait for agent").
  • 6. If it finished, the call returns and Layer 1 replies to the SP. If it parked, the call also returns — but that database row outlives the request, the deploy, and the restart.
  • 7. Two hours later the agent finishes. Layer 8 calls taskService.complete(taskId). Flowable finds row #4471, resumes from exactly that node, runs the remaining steps, ends the process.
  • Step 7 is the entire reason this layer exists. Nothing else in the stack can do that.

"The diagram is the executable" — the concrete version

  • Here is the same decision written twice. Plain Java: var c = classifier.classify(freeText); if (c.confidence >= 0.7) { ... } else { escalateToAgent(); }
  • BPMN XML — what actually runs: a <serviceTask> carrying flowable:delegateExpression="${classifyDelegate}", an <exclusiveGateway>, and two <sequenceFlow> elements whose <conditionExpression> bodies are ${confidence >= 0.7} and ${confidence < 0.7}.
  • The point: ${confidence >= 0.7} is not a comment or a label. Flowable's expression engine evaluates it at runtime against the process variables — it is the if. Change 0.7 to 0.8 in the XML, redeploy the file, and behaviour changes with no Java recompiled.
  • Likewise flowable:delegateExpression="${classifyDelegate}" is the actual dependency injection — Flowable resolves that Spring bean by name and invokes it.
  • So there is no generation step and no sync problem. The modeler renders this XML as boxes and arrows; the engine steps through the same XML. A diagram cannot drift from the code, because the diagram is the file.

Where L1 and L2 concerns are configured — a sixth table

  • The L1/L2 taxonomy is currently implied everywhere and defined nowhere. Six places need the same list: Layer 1 (render the menus), Layer 3 (pick which BPMN process to start), Layer 4 (DMN inputs), Layer 5b (/classify-intent matches free text against the whole taxonomy), Layer 7 (one Togglz flag per L2 concern), Layer 2 (stored on HelpSession.l1Concern and Ticket.l1/l2).
  • That needs a single source of truth — a concern_catalogue table, one row per L2 concern.
  • Important consequence: adding a new L2 concern is never a pure config change. A new row is useless without a BPMN process, a DMN table, an action executor and a Togglz flag — all of which need a deploy. What the table buys is that labels, ordering and enable/disable are tunable, and that all six layers read one list instead of six drifting copies.

Worked example — how "Remove strike" resolves, end to end

  • The question this answers: once the SP picks L1=STRIKE, L2=REMOVE_STRIKE, how does the system know to read the strike table, apply strike conditions, and pick a tier? There is a step between "I know the concern" and "I know what to check" — and it needs a named mechanism.

Step 3 — Fact Providers, the missing mechanism

  • Every concern needs different data. Leave fine reads the fines table; strike removal reads the strike table; transport reads the booking. Thirty concerns means thirty different fetches — but you don't want thirty delegates hardcoded into BPMN diagrams.
  • The pattern: one interface ConcernFactProvider with String concernCode() and Map<String,Object> fetchFacts(FactRequest). One implementation per concern. Spring injects all of them into a map keyed by concern code.
  • StrikeFactProvider returns strikeExists, strikeReasonCode (NO_SHOW/LATE/SYSTEM_ERROR…), strikeAgeDays, strikeCountLast90Days, priorAppealCount.
  • One generic delegate serves all thirty concerns: fetchFactsDelegate reads l2Concern from the process variables, looks up the right provider, and copies the returned facts into process variables via facts.forEach(ex::setVariable).
  • So the answer to "how does it know to check the strike table" is: a Spring bean registered under the concern code, resolved at runtime. Adding a concern means adding one class — not editing a diagram.

The interaction contract — inbound to Flowable

  • Layer 1 → Flowable is the only entry point. It calls runtimeService.startProcessInstanceByKey(processKey, ticketId, vars) with variables: ticketId, spId, l1Concern, l2Concern, bookingId (nullable), freeText (nullable), medalBand.
  • The processKey comes from the catalogue (concern.getProcessKey()), never a hardcoded string — that's the link between the table above and the engine.
  • The businessKey is the ticketId. That single choice is what later lets Layer 8 find the parked process without storing a Flowable ID anywhere in our own schema.
  • A design decision buried in the return path: you might expect Layer 1 to read process variables for the answer. That breaks — when a process completes, Flowable deletes its runtime row and the variables go with it. So the rule is: Flowable's last Service Task writes the nextStep descriptor onto the HelpSession before ending, and Layer 1 re-reads the HelpSession. That works identically whether the process finished (T1/T2) or parked (T3) — Layer 1 never needs to know which.
  • Layer 8 → Flowable is the resume path: taskService.createTaskQuery().processInstanceBusinessKey(ticketId).singleResult(), then taskService.complete(taskId, {agentOutcome, agentId}). That's the entire inbound surface — two calls.

Summary — what this layer is

  • A library, not a service. flowable-spring-boot-starter as a Maven dependency inside the BOTIn backend JVM. Nothing new to deploy, no license cost.
  • Its real job: turn each L2 concern into a persisted state machine. The BPMN diagram isn't documentation that describes the flow — it is the executable.
  • State lives in the database, not in memory. A process instance waiting at a T3 User Task is a row in ACT_RU_EXECUTION, not a parked thread. That's the actual reason to use an engine instead of hand-rolling: a ticket can wait two days for an agent, across three app restarts, and resume correctly.
  • It supplies three things you'd otherwise have to build: human task queues, timers, and retry-with-dead-letter on failed steps.
  • It is the hub of the whole system — nearly every other layer is called by Layer 3 rather than calling it.

Who touches this layer, and why

API surface

  • Exposes zero HTTP endpoints. Like Layer 2, it's reached only through in-process Java calls.
  • Inbound, from Layer 1: runtimeService.startProcessInstanceByKey(key, variables) — returns once the process completes or hits a wait state.
  • Inbound, from Layer 8's callback: taskService.complete(taskId, variables) — resumes a process parked at a User Task.
  • Outbound: nothing directly. Flowable never makes a network call itself — it invokes JavaDelegate beans, and those hold the HTTP clients. Keeps the engine ignorant of transport concerns.
  • Also used operationally: historyService for querying what a finished instance did — useful for debugging a specific ticket's path.

The decision that matters — what runs on the SP's HTTP thread

  • Layer 1's POST /help/sessions/{id}/input is synchronous — the SP is watching a spinner. Flowable by default runs a process on the calling thread until it completes or reaches a wait state. So the design question is where we deliberately break that.
  • T1 and T2 stay fully synchronous. ~1.5s for "your fine has been waived" is normal app latency, and the SP genuinely wants the confirmation in that response rather than a "we'll get back to you."
  • The T3 telephony call is marked flowable:async="true". Otherwise the Exotel call sits on the SP's request thread, and a slow vendor holds the "connecting you to an agent" message hostage. Async hands it to the job executor and returns immediately.

Retry semantics — and why they're dangerous without Layer 2

  • If a JavaDelegate throws on an async job, Flowable retries (3 attempts by default), then parks it as a dead-letter job for manual inspection. Genuinely useful resilience, free.
  • And a hazard on the money path: if the ledger call succeeded but its response was lost, a retry would credit twice.
  • Flowable's retry and Layer 2's idempotencyKey are a designed pair, not two independent features. The retry is safe only because the committed TicketAction row makes the second attempt a no-op. Neither mechanism is complete without the other.

Open question — one process per concern, or one parameterized process?

  • The BRD has roughly 30 L2 concerns across four waves. Two viable shapes, and this shouldn't be decided in passing.
  • One BPMN diagram per concern: ~30 diagrams eventually. Keeps the "ops reads the diagram for this specific concern" benefit fully intact, but it's 30 files to maintain and most share the same shape.
  • One parameterized process — classify → decide → act → confirm, concern as a process variable, a dispatching ActionExecutorDelegate. Far less to maintain, but the diagram becomes abstract and the "diagram is the spec" argument that justified picking Flowable gets noticeably weaker.
  • Current lean: one parameterized skeleton with per-concern DMN tables carrying the variation — but flagged as a real trade-off, not a settled call.

Two operational facts nobody has specified yet

  • Process versioning. Deploy a new BPMN file and Flowable versions it; instances already running continue on the old version. So a T3 ticket waiting two days is executing v1 while v2 is live. Correct behaviour, but it means a bug fix does not retroactively apply to in-flight tickets — worth knowing before the first production hotfix.
  • History tables. Flowable writes ACT_HI_* rows on every transition, and the default history level is FULL — expensive and unbounded. Should almost certainly be AUDIT, with a cleanup job. Same conversation as Layer 2's retention story, and worth settling together.

Pros & cons

Pros

  • Process state survives restarts and deploys — the T3 wait is genuinely durable, not a parked thread.
  • Human task queues are a native primitive; "route to Agent 2 by medal band" is configuration, not code.
  • Retry + dead-letter on failed steps comes free, and composes correctly with Layer 2's idempotency.
  • Timers are available for free — abandoned sessions and agent SLAs need no scheduler.
  • No new infrastructure, no license cost, no separate service to operate.

Cons

  • A DB write on every node transition — chatty compared with plain Java, and it shares the DataSource with everything else.
  • ACT_HI_* grows unbounded at default settings; ignoring it is a slow-motion outage.
  • BPMN XML is verbose and unpleasant to hand-edit; realistically needs the modeler.
  • Debugging is harder than reading a stack trace — a failure is a dead-letter job plus a diagram, not a single call path.
  • Version-pinning of in-flight instances is correct but surprising, and will confuse whoever ships the first hotfix.
  • One more system whose failure modes the solo developer has to know deeply.

R&D for scale / efficiency

  • Set the history level deliberately — benchmark AUDIT vs FULL on a realistic flow and pair it with a scheduled cleanup, before the tables make it urgent rather than optional.
  • Configure the async job executor for multi-pod EKS — pool size, acquisition intervals, lock duration. Defaults assume a single node; two pods with default settings will contend for jobs.
  • Settle one-process-per-concern vs parameterized before authoring the second Wave-1 diagram — retrofitting the choice across 30 concerns is much worse than deciding it at three.
  • Add boundary timer events: close abandoned sessions parked mid-flow, and re-queue or escalate a T3 User Task no agent picks up within N minutes. Both are capabilities already paid for and currently unused.
  • Load-test the job executor specifically, not just the HTTP layer — the failure mode under load is a growing job backlog, which is invisible from request-latency metrics alone.
  • Decide the BPMN authoring workflow for a solo developer — web modeler with files committed to the repo is the usual answer, but it needs to be a deliberate choice so diagrams and code never drift.
  • Dead-letter job monitoring — a parked job is silent by default. It needs a Layer 9 metric and an alert, or failures will sit unnoticed.

Layer 4 · partial

Decision Logic — DMN

The thing to see first: they don't look alike

  • BPMN (Business Process Model and Notation) renders as a flowchart — boxes and arrows, a path through time.
  • DMN (Decision Model and Notation) renders as a table — a grid of conditions and outcomes, no sequence at all.
  • That difference is the whole reason both specifications exist. A process has an order; a decision doesn't.

BPMN — boxes and arrows

  • Its XML: <serviceTask id="classify" flowable:delegateExpression="${classifyDelegate}"/>, an <exclusiveGateway/>, and <sequenceFlow> elements carrying <conditionExpression>${confidence >= 0.7}</conditionExpression>.

DMN — a grid, not a flowchart

  • Same process, the decision step. This is exactly what the modeler shows — ⇥ marks input columns, ⇤ marks outputs.
leave-fine-genuine.dmn — hit policy: FIRST
⇥ category⇥ confidence⇥ claimFreq30d⇥ medalBand⇤ tier⇤ action
1–< 0.7––"T3""route_agent"
2"health_issue">= 0.7<= 2–"T2""waive_fine"
3"health_issue">= 0.7> 2"TITANIUM","QUEEN""T2""waive_fine"
4"health_issue">= 0.7> 2–"T3""route_agent"
5"family_emergency">= 0.7<= 1–"T2""waive_fine"
6––––"T3""route_agent" (catch-all)

Four DMN concepts that don't exist in BPMN

  • Input columns vs output columns. The ⇥ side is what you feed in, the ⇤ side is what comes out. Every modeler separates them visually.
  • Rules are rows. Row 3 above encodes "a Titanium or Queen SP gets the benefit of the doubt even with a high claim rate" — one row, no code.
  • Hit policy decides what happens when several rows match. FIRST takes the topmost, which means row order is semantically significant — specific rules go above catch-alls, and row 6 must stay last. Other policies exist (UNIQUE, ANY, COLLECT, PRIORITY); FIRST is right here.
  • FEEL — Friendly Enough Expression Language, the syntax inside the cells: >= 0.7, <= 2, "TITANIUM","QUEEN" (an OR list), and – meaning don't care. Deliberately simple enough that an ops person can read a column without knowing Java.

The DMN XML — same "the file is the executable" property

  • Structure: <decision> wraps a <decisionTable hitPolicy="FIRST">, which contains <input> and <output> declarations followed by one <rule> per row, each holding <inputEntry> and <outputEntry> cells in column order.
  • <inputExpression><text>category</text></inputExpression> reads the process variable named category — that's the join between Layer 3 and Layer 4.
  • A cell is literally <inputEntry><text>&gt;= 0.7</text></inputEntry>. Change it to >= 0.8, redeploy the file, behaviour changes — no Java recompiled. Identical to the BPMN gateway expression.

One DMN feature we're not using — the DRD

  • DMN also has a DRD (Decision Requirements Diagram), and that one is a boxes-and-arrows picture — it shows decisions feeding other decisions, e.g. [Claim risk score] and [SP standing] both feeding [Genuine case?].
  • You'd need it if the claim-history scoring idea from the industry study ever becomes its own decision feeding the main table.
  • Right now there's one decision per concern, so a single table is all the DMN we need — worth knowing the DRD exists so the modeler's second tab isn't a mystery.

Layer 5 · partial

The Python Service — Language Understanding Only

Start here — why it exists at all

  • The menu path needs no AI. SP taps "Fines" → "Leaves fine" and we know exactly what they want. That's a string comparison.
  • The problem appears in exactly two places where input isn't a menu selection. (1) Free text explaining why: "I was sick yesterday" — the concern is already known, but the DMN table needs a reason category to decide. There's no menu for reasons because reasons are open-ended in phrasing while closed in category. (2) Free text as the first message: "mera aaj strike laga hai usko hatao" — no concern selected at all.
  • Both are the same underlying problem: turning unconstrained human language into one value from a fixed list. That is the entire job of this layer.

Why not just do it in Java

Three ways to solve it, and why two of them fail here
ApproachWhy it fails / works
Keyword matching"sick", "bimar", "tabiyat kharab", "not well", "fever", "hospital" — endless variants, and the SOP already shows SPs mixing Hindi, English and Hinglish in one sentence
Classical NLU (Rasa, Dialogflow)Needs labelled training data you don't have, needs retraining as phrasing drifts, and handles code-switching poorly
An LLM callWorks with zero training data; handles Hindi/English mixing natively; you describe the categories in the prompt rather than training a model

Why a separate service — honestly

  • You could call an LLM's HTTP API from Java, so the separate deployable needs a real justification.
  • The safety boundary is physical, not conventional. Python has no database credentials and no action capability. It can misclassify; it structurally cannot move money.
  • Independent deployment. Swap the model or tune a prompt without redeploying the service that waives fines.
  • Library maturity. Pydantic guarantees the response shape; vendor SDKs are best-supported in Python.
  • The honest counter-argument: a well-isolated Java package could achieve most of that. The separate service makes the boundary enforced by architecture rather than by discipline. Defensible — not a slam dunk.

When it's touched — by input shape, not by tier

  • The framing that matters: Python isn't called based on tier. Tier is an output of the flow; the Python call happens near the start, driven by whether free text is present.

  • A fully menu-driven T2 session (a concern with a reason dropdown instead of a text box) would touch Python zero times.

What it explicitly does not do

  • Doesn't decide anything. DMN decides. Python only says "this text means health_issue."
  • Doesn't touch the database. No credentials.
  • Doesn't take actions. Cannot waive a fine.
  • Doesn't generate text for the SP. Responses come from templates.
  • Doesn't summarize conversations for agents. extractedReason already serves that — see Layer 8.

The confidence score isn't decoration

  • It is the input to Trigger C. Below threshold → route to a human. That's how the system fails safe when language understanding is uncertain, rather than acting on a guess.
  • When the service is down or slow: the Resilience4j circuit breaker trips and the flow routes to T3. Same pattern as the Togglz kill switch — degrade to a human, never break. A Python outage means slower SP resolution, not wrong money movement.

Should it write the reply to the SP? — No, deliberately

  • 1. Hallucinated numbers. "₹200 has been credited to your wallet." If the LLM writes that sentence it can write the wrong amount. A template with {amount} structurally cannot.
  • 2. Unauthorized commitments. An LLM might helpfully add "we'll review your other fines too." Nobody promised that and nothing will honour it. Templates can only say what someone approved.
  • 3. Non-determinism kills auditability. With generation, "what do we tell SPs when a leave fine is waived?" has no answer — it varies every time. With templates it's a string in a file you can show someone.
  • 4. The dispute problem. An SP says "the bot told me my fine was cancelled." ConversationMessage records the text either way, but a template is reviewable in advance; generated text is only reviewable after the fact.
  • 5. Latency and cost on every interaction. Today T0 and T1 make zero LLM calls. Generating responses would add one to every single resolution — a few hundred ms and a per-call cost on the highest-volume paths, for cosmetic benefit.
  • 6. Untestable. You can assert a template renders correctly. You cannot unit-test "the model said something reasonable."

What we do instead — templates keyed by the DMN action

  • action=waive_fine → "Your ₹{amount} fine for {date} has been waived."
  • action=explain_no_strike → "We couldn't find an active strike on your account."
  • action=explain_too_old → "This strike is from {date} and is outside the {days}-day appeal window."
  • action=route_agent → "Connecting you to an agent…"
  • Scale check: ~30 concerns × ~3–4 outcomes ≈ 100 distinct messages. That's a content problem, not a generation problem — entirely tractable.
Four options considered, and the verdict on each
OptionWhat it meansVerdict
A. Templates onlyFixed strings + variables, one set per languageRecommended
B. LLM localizes at runtimeApproved English template → LLM renders it in Hinglish liveRejected — translation can still mangle a number, and it adds a call to every interaction

The language question — solved by classification, not generation

  • The SOP shows SPs writing in Hindi, English and Hinglish. Should the reply match? Yes — and that's classification, not generation.
  • Add a detectedLanguage field to the /classify response. It picks one value from a fixed list (hi / en / hinglish) — exactly what this service already does. Java then selects the matching template.
  • That keeps the boundary intact: Python understands language, Java produces it.

Where an LLM would write to the SP

  • Wave 4's open-ended "Other any issue" bucket — Layer 13. If an agent is ever built for arbitrary SP questions, generation is inherent to it, because there's no fixed outcome set to template against.
  • That's the same boundary that made RAG a Wave-4-only fit: fixed outcomes → templates; open-ended outcomes → generation.

What we give up

  • Honestly: naturalness. Templates read as templates. An SP who wrote a long emotional message gets back a clean, slightly formal sentence. That's a real cost — just a smaller one than a wrong number in a financial message.

Layer 7 · partial

Safety — Kill Switches (Togglz)

Start here — the problem

  • Wave 1 is live. Leave-fine auto-waive is running. At 2am you discover it's waiving fines it shouldn't — a bad DMN row, the fines API returning stale data, or an abuse pattern nobody predicted. Money is moving incorrectly right now.
  • Without a feature flag: revert the commit, rebuild, redeploy — fifteen to thirty minutes in most orgs, with money moving that whole time. Even a config table doesn't help if reading it needs a restart.
  • With a feature flag: flip a switch, effect is immediate. Seconds.
  • That gap — between "we noticed" and "it stopped" — is the entire value proposition. For a system that moves money automatically without human review, it's the difference between an incident and a catastrophe.

What Togglz literally is

  • A Java library: togglz-spring-boot-starter in pom.xml. Same shape as Flowable — a JAR inside your app, no server to run.
  • Piece 1 — a Feature enum. You declare flags in code: public enum BotinFeature implements Feature { @Label("Leave fine — auto waive") LEAVE_FINE_AUTO_WAIVE, ... }
  • Piece 2 — a StateRepository. Where on/off is stored. We'd use JDBCStateRepository: one small table in the same database. (Also available: in-memory, file, Redis.)
  • Piece 3 — the admin console. Togglz ships a web UI at /togglz-console with a toggle per feature. This is what makes it operationally real: ops flips the switch, not a developer.

Activation strategies — how this maps to the BRD's rollout plan

  • Togglz isn't only on/off — each flag has a strategy deciding who sees it.
Built-in strategies, and which ones this project actually needs
StrategyWhat it doesOur use
Always on / offThe obvious oneKill switch
Gradual rolloutActive for N% of users, by a hashThe BRD's "ramp by %, not 100% on day one"
Username / roleActive only for named usersInternal testing before SP exposure
Server IPActive only on some hostsCanary a single pod
Custom scriptYou write the predicateMedal-band ramp
  • The last row matters: the BRD says ramp "by % or by medal band." Percentage is built in; medal band needs a custom ActivationStrategy plus a UserProvider exposing the current SP's medal band. Both are small classes — but they're work, not configuration.

Where the check sits in the flow

One real tension — enum constants vs catalogue strings

  • Togglz is enum-based — compile-time constants. But concern_catalogue.togglz_flag stores flag names as strings, resolved at runtime. Those don't fit together directly.
  • The resolution is Togglz's NamedFeature: featureManager.isActive(new NamedFeature(concern.getTogglzFlag())).
  • The cost: that bypasses the enum's type safety — a typo in a catalogue row becomes a silent "feature not found" rather than a compile error. Mitigation: a startup validation that every togglz_flag value in the catalogue matches a declared enum constant, failing fast if not.

What Togglz is not

  • Not a config system. It's boolean. "Set the confidence threshold to 0.8" is not a Togglz job — that's DMN or application config.
  • Not permissions. It gates features, not users' rights.
  • Not A/B testing. It can split traffic; it doesn't measure outcomes. That's Layer 9's job.
  • Alternatives — Unleash, Flagsmith, LaunchDarkly — are all separate services. Togglz was chosen for the same reason as Flowable: Java-native, free, no new infrastructure.

Pros & cons

Pros

  • Seconds, not deploys, between noticing a problem and stopping it — on the one path that moves money.
  • Ops can flip it without a developer, which is what makes it usable at 2am.
  • Gradual-rollout strategy gives the BRD's percentage ramp for free.
  • No new infrastructure — a JAR and one table.
  • Off degrades to human handling rather than an error, so flipping it is low-regret.

Cons

  • The console can disable money-moving features — it needs real authentication, which is currently Layer 11's undesigned territory.
  • NamedFeature lookups lose compile-time safety; a catalogue typo fails silently without the startup check.
  • Flag debt: flags accumulate and nobody removes them, so the codebase slowly fills with dead branches.
  • Medal-band ramping isn't built in — it needs a custom strategy and a UserProvider.
  • Flag state is a database read; Togglz caches it, so a flip isn't literally instant — it's instant plus the cache TTL.

R&D for scale / efficiency

  • Tune the cache TTL deliberately — it's the real latency between flipping the switch and the bleeding stopping. Too long defeats the purpose; too short means a DB read on every action.
  • Secure the console before Wave 1 — an unauthenticated /togglz-console is a way to disable fraud controls. Ties directly to Layer 11.
  • Add flip auditing. JDBCStateRepository stores current state only, not history. For a money-moving flag you want who flipped it and when — that's a custom repository wrapper or a DB trigger, and it doesn't exist by default.
  • Write the startup validation reconciling concern_catalogue.togglz_flag values against declared enum constants — cheap, and closes the NamedFeature safety hole.
  • Build the medal-band ActivationStrategy and its UserProvider before the ramp, not during it.
  • Set a flag lifecycle policy — e.g. remove a flag once its feature has been stable for N weeks — or flag debt accumulates silently.
