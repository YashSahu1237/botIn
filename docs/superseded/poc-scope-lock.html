In and out

In scope

  • T1 — explain (no fine found, already refunded, outside window)
  • T2 — automatic fine refund
  • T3 — route to a human agent
  • Six reason categories, classified from free text
  • Test SP accounts only
  • curl / Postman as the client, plus an optional demo page
  • English response templates

Out of scope

  • T0 — not applicable; leave fine always creates a ticket
  • Rule-break fine (30.2%) — the next concern, not this one
  • Leave hata dijiye — separate concern
  • Telephony, agent screen, mobile app
  • Observability, access control, LLM guardrails
  • Hinglish templates — Wave 1 work
  • The Hydra & Spa medical-report variant
Hard boundary

No real Service Partner ever interacts with this POC, and no production money moves. Every run is driven by a test client against test SP accounts, with the refund pointed at a non-production system throughout.

If that changes, this is no longer a POC and needs the safety scaffolding — kill switches, reconciliation, access control — that is explicitly excluded above.

A finding worth flagging before we start

"How to refund fine — Admin → Escalation → View SP Escalation → Select date in data range → click on refund fine" SOP tab · Leaves fine · Step 3 note

The SOP documents the refund as an admin UI click-path, not an API call. That is not proof no service method exists behind it, but it is the strongest signal so far that the refund integration may need building rather than integrating. The POC's empapi audit now has a specific thing to look for, and the estimate for that layer may need revising afterwards.

What the SOP already gives us

Two response templates are already written, in Hinglish, and both end with a CSAT prompt:

Refund done"Aapka fine refund kar diya gaya hai."

"Already refunded" is a documented real scenario — the partner asking again for something that has already been done. It becomes a DMN row, and it doubles as a free test case for the idempotency work later in the build.

Three questions this document cannot answer

These need a decision from someone other than the developer before the scope is genuinely locked.

  1. Is the Hydra & Spa exception in or out? The SOP carves it out: fines there are refunded only after validating genuine medical reports. That is document review, a materially different problem. Recommendation: exclude — but it is an ops call, not an engineering one.
  2. What does Strike Concern = Yes mean on all four leave-fine sub-scenarios? If a refund must also reverse a strike, that is a second backend action and it expands the integration work. Needs clarifying before the action executor is designed.
  3. Does a service method exist for the refund, or only the admin UI path? Answerable by inspecting empapi. The answer does not block the POC — the interface boundary absorbs either outcome — but it changes the estimate for production.

Sign-off
